# State Management

On my workshop page, I can type a search query, expand a card and see how many seats are available. Each of these values can change, but they belong in different places. I ask who reads or changes the value, where its authoritative value comes from and whether I can calculate it from data I already have.

## 1. Local vs shared state

I keep **local state** inside the component that uses it. If each workshop card can expand its own schedule, I let each card track whether it is expanded. Expanding one card has no effect on the others.

I use **shared state** when multiple parts of the UI need the same value. The search box edits the query, the list uses it to filter workshops and the results summary uses it to explain what is shown. I keep the query in their nearest common parent and pass the value and update function down as props.

```text
WorkshopsPage owns query
├── SearchBox       reads query and asks the page to update it
├── WorkshopList    receives the filtered list
└── ResultsSummary receives the result count
```

I lift state when components need to agree. If only one card can stay open at a time, I move that decision to the list and store one `expandedWorkshopId`. Each card receives its expanded status from the list. I can share state within one page through its parent without introducing an app-wide store.

## 2. Derived state

When I can calculate a value from current inputs, I derive it. I keep the query and the workshop list as inputs. The filtered list and its count come from those two values.

```javascript
function getWorkshopResults(workshops, query) {
  const search = query.trim().toLowerCase()
  const visibleWorkshops = workshops.filter((workshop) =>
    workshop.title.toLowerCase().includes(search)
  )

  return {
    visibleWorkshops,
    resultCount: visibleWorkshops.length
  }
}

const workshops = [
  { id: 1, title: "HTML and CSS" },
  { id: 2, title: "Browser Rendering" }
]

const { resultCount } = getWorkshopResults(workshops, " CSS ")
console.log(resultCount)
```

I get `1`. If I clear the query, both workshops match. If new workshop data arrives, I calculate the result from the latest list and the same query. If I stored the count separately, I would have to remember to update it on both changes.

I start by calculating the result when I render. If profiling shows the calculation takes noticeable time, I can reuse the result while the relevant inputs stay the same.

## 3. Server state vs UI state

I call data **server state** when the server holds the authoritative value. My frontend can keep a cached copy of the workshop list and available seats, but someone else might book a seat while my page is open. I decide when to fetch again and how to show loading, errors and any previously loaded data.

I call values **UI state** when they describe what the user is doing or seeing in this interface. My search query and expanded card are examples. A value can be shared UI state even if the API uses it as a request parameter. I can put the query in the URL when I want the filtered view to survive a reload or be shareable.

| Value on my page | Where I keep it |
| --- | --- |
| Whether a card is expanded independently | Local UI state in that card |
| Search query used by multiple components | Shared UI state on the page or in the URL |
| Available seats | Server state with a client-side cached copy |
| Visible workshops and result count | Derived from the fetched list and the query |

When I submit a booking, I show that the action is pending. Once the server confirms it, I use the returned seat count or fetch the workshop again. If someone booked the last seat first, I show the server's response and refresh availability. This keeps the booking decision with the server while my UI handles feedback.

## 4. Rendering strategies

When someone opens a workshop URL, I ask where the first useful HTML comes from and when it was generated. I can answer those questions separately for each page in the app.

| Strategy | How the first useful HTML is produced | Where I use it |
| --- | --- | --- |
| Client-side rendering (CSR) | The browser loads the page shell and JavaScript. The JavaScript fetches the data and builds the view in the browser. | A signed-in dashboard where users interact with filters and regularly fetch updated data |
| Server-side rendering (SSR) | The server uses data available during the request to generate HTML and sends it to the browser. | A confirmation page that needs the user's session and the latest booking status before showing content |
| Static site generation (SSG) | The build generates HTML ahead of time. The server or CDN serves the same file until I publish a new version. | A workshop guide that changes only when I edit and publish it |
| Incremental static regeneration (ISR) | I serve cached static HTML and regenerate a page after deployment, according to the platform's revalidation rules. | Public workshop details that change occasionally and can tolerate a brief delay before edits appear |

### How I choose for my workshop app

- **CSR for `/dashboard`.** I return the app shell, then fetch the signed-in user's bookings in the browser. While I wait, I show a loading state. Once the response arrives, I render the bookings or an appropriate empty or error state. I accept the initial wait because the page is private and most of the work happens after sign-in.
- **SSR for `/bookings/42`.** I read the session on the server, check whether the user owns the booking and fetch its current status. I send HTML that already says “Confirmed” or “Pending”. I keep this personalized response out of shared caches. The browser can still run JavaScript for actions like cancelling the booking.
- **SSG for `/workshop-guide`.** I turn the guide into HTML during the build. A visitor can read it immediately from the served file. An edit appears when I build and deploy the updated guide.
- **ISR for `/workshops/42`.** I cache the public HTML with a 60-second revalidation interval. Suppose the page was generated at 10:00:00 and I change its description at 10:00:30. In a request-triggered setup that serves stale content during regeneration, a visit at 10:01:05 can receive the old HTML and trigger a refresh in the background. A later visit gets the new description after regeneration succeeds. I fetch the live seat count separately and let the server enforce availability when someone books.

```text
CSR   request → HTML shell → browser runs JS and fetches → view
SSR   request → server reads data and renders → HTML
SSG   build → saved HTML → requests read the saved file
ISR   request → cached HTML
                     └── eligible to revalidate → regenerate → replace cache
```

I can combine these on one page. I serve the public workshop description as static HTML and fetch the seat count in the browser. If a framework hydrates the page, its JavaScript connects interactive behavior to the HTML that was already sent. Rendering and hydration are separate steps. [Next.js guide to incremental static regeneration](https://nextjs.org/docs/app/guides/incremental-static-regeneration)

## 5. Build tooling

My workshop list is the first screen, and I have a report preview that only organizers open. I want the list to work on the first visit and the preview code to arrive when someone asks for it.

| Build concept | What I do in this app |
| --- | --- |
| Bundling | I give the bundler an entry module. It follows imports and emits browser-ready files for the list and its dependencies. |
| Transpilation | I set a browser target so the build can rewrite newer syntax, such as optional chaining, if my supported browsers need it. |
| Code splitting | I put the report preview in a separate chunk so its implementation can stay out of the entry bundle. |
| Lazy loading | I request the report chunk when the organizer clicks the preview button. |
| Tree shaking | I let the production build remove unused exports when it can prove they are safe to drop. |

### How I split and load the report preview

In my page HTML I put a button with `id="preview-report"` and an output element with `id="report-output"` and `role="status"`. In the entry module, I use a normal import for code I need right away and a dynamic import for the preview. These are example source modules for the bundler.

```javascript
// main.js
import { formatTitle } from "./format.js"

document.title = formatTitle("Workshops")

const button = document.querySelector("#preview-report")
const output = document.querySelector("#report-output")

button.addEventListener("click", async () => {
  button.disabled = true
  output.textContent = "Loading preview"

  try {
    const { renderReport } = await import("./report.js")
    renderReport(output)
  } catch {
    output.textContent = "Could not load the preview. Try again or reload the page."
  } finally {
    button.disabled = false
  }
})
```

```javascript
// report.js
export function renderReport(output) {
  output.textContent = "Workshop report preview"
}
```

```javascript
// format.js
export function formatTitle(title) {
  return title.trim()
}

export function formatCsvCell(value) {
  return '"' + String(value).replaceAll('"', '""') + '"'
}
```

The bundler can include `formatTitle` in the initial code and emit a separate chunk for `report.js`. The click controls when I load that chunk. If no module uses `formatCsvCell`, a production bundler can remove that export. Static ES module imports and exports help it see what is used. I keep intentional side effects, such as registering a global listener, visible to the build so it does not mistakenly discard them. [webpack code splitting](https://webpack.js.org/guides/code-splitting/) · [webpack tree shaking](https://webpack.js.org/guides/tree-shaking/)

### How I check browser support and the output

If my target needs optional chaining transformed, the build can rewrite `workshop.instructor?.name` into an equivalent guarded access. A missing built-in such as `Array.prototype.at` needs a compatible implementation, commonly provided by a polyfill. I check syntax support and built-in support separately. [Babel browser targets and transforms](https://babeljs.io/docs/babel-preset-env/)

I inspect the production build and open DevTools Network with the cache disabled. On reload I look for the entry script. Then I click the preview button and check whether the report chunk appears. I also check the production bundle to see whether the unused formatter was dropped. If I split a feature that almost everyone opens immediately, I compare the initial bundle savings with the extra wait on the first interaction.
