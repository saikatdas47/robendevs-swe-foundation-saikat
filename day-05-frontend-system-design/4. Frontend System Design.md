# Frontend System Design

I use the same design steps for a feed, a search box, a chat and a product page. The steps help me find what each screen needs from its API and what can stay inside the browser.

## 1. My design approach

| Step | What I work out |
| --- | --- |
| Requirements | I list the main user actions and decide what must work on a slow connection, with the keyboard or after a reload. I agree on freshness and latency targets. |
| Component architecture | I draw the screen as a tree and decide who owns state. I give reusable components clear inputs and keep page-wide coordination in the page or a shared data layer. |
| Data model | I identify entities, stable IDs, relationships and ordering. I keep server data separate from details such as an open filter panel. |
| API interface | I specify the request, response, pagination, failure states and what happens if the client retries. I state which values the server owns. |
| Optimisations | I measure a representative path first. If the slow part is a large DOM, I look at virtualisation. If it is a slow network request, I check caching, payload size and latency. |

For a feed, I write down the flow I expect. It gives me a place to put error handling and measurements.

```text
User asks for more → feed page calls API with cursor
                  → cache merges posts by ID
                  → visible rows render
```

## 2. Real-time data

I choose based on how fresh the data needs to be and whether updates need to travel both ways.

| Approach | What happens over the network | Where I use it |
| --- | --- | --- |
| Polling | The client asks on a timer. Each response finishes immediately with the current state. | An order status display that can be several seconds behind |
| Long polling | The server holds the request until it has an update or hits a timeout. The client then opens another request. | A mostly idle event stream when I need a request-response fallback |
| Server-Sent Events (SSE) | The server keeps an HTTP response open and sends events to the client. The client can send commands through separate HTTP requests. | Live delivery updates or a notification count |
| WebSockets | The client and server keep a connection open and can both send messages independently. | Chat with messages, typing and presence in both directions |

With five-second polling, a change can wait almost five seconds before the next poll, plus network time. I avoid overlapping requests and slow the polling down when the tab is hidden. With long polling, I reopen the request after the response and back off after network errors. The server's wait should fit inside any proxy timeout.

For SSE, I can use browser `EventSource`. When the server supplies event IDs, the browser can send the last event ID on reconnection. I still need server support for replay or a way to fetch a fresh snapshot. With WebSockets, I plan for reconnects, missed events and duplicate messages. I use an event ID or sequence number to resume where possible. A live connection does not by itself guarantee that my application recovered events lost during a disconnect. [HTML Standard on server-sent events](https://html.spec.whatwg.org/multipage/server-sent-events.html)

## 3. Large lists and feeds

I separate how much data I load from how many rows I render. **Infinite scroll** loads another API page as the user approaches the end. **Virtualisation** keeps only the visible rows and a small buffer in the DOM. I can use both when the feed is long.

If my feed holds 1,000 posts and shows 12 at a time, I might render around 20 rows including the buffer. The virtual list preserves scroll space for rows outside the window. With variable-height cards, I measure their heights and reserve image space so a late image load does not move the reader away from their current post. I keep the focused item available during keyboard navigation and offer an explicit **Load more** action.

I store each fetched page by its query and cursor. For a personalised feed, the cache is also scoped to the signed-in user. I use a freshness rule to decide when to fetch again. I can evict older pages if the session grows too large. This controls memory even when the number of rendered DOM nodes is already small.

I normalise shared data when the same post can appear in several results. In this example the page keeps IDs in display order and the entity map keeps one record per post.

```javascript
const feedCache = {
  postsById: {
    p42: { id: "p42", title: "Workshop notes", liked: false },
    p43: { id: "p43", title: "Next workshop", liked: true }
  },
  pagesByKey: {
    "latest:first": { ids: ["p42", "p43"], nextCursor: "page-two" },
    "saved:first": { ids: ["p42"], nextCursor: null }
  }
}

feedCache.postsById.p42.liked = true
```

Both views now read the updated post from the same entity. If saving or liking a post changes whether it belongs in a list, I also update or invalidate that list's IDs. Normalising the entity does not recalculate list membership.

## 4. Design systems, monorepos and micro-frontends

| Choice | Why I might use it | What I need to maintain |
| --- | --- | --- |
| Design system | I reuse tokens, accessible components and interaction patterns across products. | Component documentation, versioning, accessibility checks and a way for teams to propose changes |
| Monorepo | I keep apps and shared packages in one repository so I can update a component and its callers together. | Build boundaries, ownership and CI that avoids rebuilding unrelated packages |
| Micro-frontends | I let teams own and deploy distinct parts of the frontend independently when release coordination is a real constraint. | Consistent navigation and session behavior, shared dependency compatibility, cross-app tests and bundle overhead |

I can use a design system in a single app or across many apps. A monorepo describes where the code lives. Micro-frontends describe how parts of the frontend are owned, integrated and shipped. I can keep separately deployed frontends in the same monorepo. For a small team, a modular app with shared components gives me fewer integration points to maintain.

## 5. Production concerns

| Concern | What I check |
| --- | --- |
| SEO | For a public page I use a stable URL, meaningful title and canonical URL. I make core content available in discoverable HTML, return the correct status for missing pages and add product structured data that matches the visible page. |
| Internationalisation | I keep messages separate from components, support plural forms and use `Intl` for dates, numbers and currency. I test longer translations and right-to-left layouts. |
| Security | I treat API content as untrusted and render it as text unless I have a reason to handle sanitised HTML. I keep secrets out of client code and leave authorisation to the server. For cookie-authenticated writes, I make sure the API uses CSRF protection. |
| Offline support | I can cache the app shell and selected read-only data via a service worker. I label cached content and queue writes only when retry, deduplication and conflict handling are defined. |
| Error tracking | I capture unexpected errors with the route, release and a request ID where available. I filter credentials and personal information from reports and use source maps to find the original code. |
| Real-user monitoring | I measure LCP, INP and CLS and break down slow visits by route, device and release. I compare real-user data with lab tests, then check which change produced an improvement. |

## 6. Practice designs

### News feed

- **Requirements** — I show a chronological feed with Load more and a way to see new posts without jumping the scroll position.
- **Components** — I split it into `FeedPage`, `NewPostsBanner`, `VirtualList` and `PostCard`.
- **Data and API** — I use `GET /feed?cursor=...&limit=20`, returning posts and a nullable `nextCursor`. I store posts by ID and preserve the server's order in the page data.
- **Optimisation and failure** — I keep loaded posts visible if a later page fails and retry that cursor. I use SSE for a new-post notification, then fetch the top page when the user clicks the banner.

### Autocomplete search

- **Requirements** — I show suggestions as the user types. Arrow keys move through the list, Enter selects a result and Escape closes it.
- **Components** — I use an input with a combobox pattern, a suggestion list and a status message.
- **Data and API** — I keep the query and highlighted item as UI state. `GET /suggestions?q=css&limit=8` returns a short list of IDs and labels.
- **Optimisation and failure** — I try a 200 ms debounce, cancel older requests and check that the result still matches the current query. If `cs` finishes after `css`, I ignore it. I cache recent query results briefly and let users submit the typed query if suggestions fail.

### Chat application

- **Requirements** — I load message history, send messages and show whether an outgoing message is pending, sent or failed.
- **Components** — I use a conversation list, a message timeline and a composer.
- **Data and API** — I fetch older messages through `GET /conversations/42/messages?before=...` and use a WebSocket for live messages and acknowledgements. I give each outgoing message a client-generated ID. The server uses that ID to deduplicate retries and returns its message ID and sequence.
- **Optimisation and failure** — I show the outgoing message as pending immediately, reconcile it on acknowledgement and resume from the last received sequence after reconnecting. I page older history and preserve the scroll anchor when I prepend it.

### E-commerce product page

- **Requirements** — I show discoverable product details, let users pick a variant and explain when a price or stock level changes.
- **Components** — I separate the product gallery, product details, variant picker and Add to cart action.
- **Data and API** — I keep the selected variant as UI state. `GET /products/desk-lamp` gives me details and variants. `POST /cart/items` receives the variant ID and quantity, and the server checks price and stock before accepting it.
- **Optimisation and failure** — I serve public product HTML through SSR or static regeneration depending on freshness. I fetch current availability for the selected variant and optimise the main image for LCP. If adding to the cart fails, I keep the user's variant selected and show what changed.
