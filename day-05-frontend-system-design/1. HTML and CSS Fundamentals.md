# Day 05 — HTML and CSS Fundamentals

I use a small workshop signup page to connect the two topics. I start with HTML so the page has a clear structure and works with a keyboard. Then I use CSS to arrange the content and let the layout change with the space available.

## 1. Semantic HTML

I choose an element by the job it does on the page. A browser can expose the meaning of native elements to assistive technology. For example, a screen reader can let someone jump directly to the main content or navigate through headings.

| Element | When I use it |
| --- | --- |
| `header` | Introductory content for the page or a section |
| `nav` | A major group of navigation links |
| `main` | The primary content of the page |
| `section` | A group of content on one topic, usually with a heading |
| `article` | A self-contained piece such as a post or an announcement |
| `aside` | Related material such as a sidebar |
| `footer` | Closing information for the page or a section |
| `div` | A generic wrapper when I only need grouping or layout |

For the signup page, I use this outline.

```text
header
└── nav
main
├── h1  Frontend Workshop
├── section
│   └── h2  What I will learn
└── section
    ├── h2  Sign up
    └── form
footer
```

I use an `<a href="…">` when the user needs to navigate somewhere. I use a `<button>` for an action such as opening a menu or submitting a form. A native button already has keyboard behavior, so I get focus and activation without writing that behavior myself.

## 2. Forms and accessibility

### How I connect a label to a field

I give the field an `id` and put that same value in the label's `for` attribute. This gives the input an accessible name and lets the user focus it by clicking the label. The field's `name` serves a different purpose. It becomes the key used when the browser sends the value.

```html
<section>
  <h2>Sign up</h2>

  <form action="/signup" method="post">
    <label for="signup-email">Email address</label>
    <input
      id="signup-email"
      name="email"
      type="email"
      autocomplete="email"
      required
    >

    <fieldset>
      <legend>Preferred session</legend>

      <input id="morning" name="session" type="radio" value="morning" required>
      <label for="morning">Morning</label>

      <input id="afternoon" name="session" type="radio" value="afternoon">
      <label for="afternoon">Afternoon</label>
    </fieldset>

    <button type="submit">Sign up</button>
  </form>
</section>
```

I use `fieldset` and `legend` to give the radio group a shared question. The radios use the same `name`, so the user selects one session. I keep labels visible while the user types. If I use a placeholder, I treat it as a hint about the expected format.

When I submit, the browser checks that the required fields have values and that the email looks like an email address. Then it sends the named values to `/signup`. That path is an example and needs a server handler to save the signup. I validate the values again on the server because someone can send a request directly. If a field is invalid, I show a plain-language error beside it and can associate that message with `aria-describedby`.

I use `GET` for a read-only form like search, where the values can go in the URL query string. For a signup that creates a record, I use `POST`.

### How I write alt text

I write alt text based on what the image contributes in context.

- For an informative photo, I describe the detail the reader needs, such as `alt="Workshop entrance on the ground floor next to the ramp"`.
- For a decorative image, I use `alt=""` so assistive technology can skip it.
- If an image is the only content of a link or button, I describe what it does, such as `alt="Workshop home"` for a logo linking to the homepage.

### How I check headings and keyboard access

I use `h1` for the page title, `h2` for its main sections and `h3` for a subsection inside an `h2`. I pick the level by where the heading fits in the outline, then style its size with CSS. I avoid jumping from `h2` to `h4` when starting a subsection.

I press Tab through the links, fields and buttons to see whether focus is visible and follows the reading order. I try submitting the form with an empty field and check whether the feedback tells me what to fix. I also check the text and focus indicators for enough contrast against their backgrounds.

## 3. CSS box model

I picture every element's box as four layers.

```text
margin    space outside the border
└── border    edge around the padded area
    └── padding   space inside the border
        └── content   text, image or child layout
```

If I set `width: 200px`, `padding: 16px` and `border: 2px solid`, the default `content-box` makes the border box `200 + 32 + 4 = 236px` wide. With `border-box`, the padding and border fit inside the declared width, so the border box stays 200px wide and the content area is 164px. Margin is outside that calculation in both cases.

```css
*, *::before, *::after {
  box-sizing: border-box
}
```

I use padding when I want more space inside a card or button. I use margin for space outside a box. In Flexbox or Grid, I often set `gap` on the container to space its items consistently.

## 4. Flexbox

I reach for Flexbox when I mainly want to arrange items along one axis, such as a row of form buttons. With `flex-direction: row` in a typical left-to-right page, the main axis runs horizontally and the cross axis runs vertically. If I switch to `column`, the main axis runs vertically.

| Property | How I use it |
| --- | --- |
| `justify-content` | Distributes available space along the main axis |
| `align-items` | Aligns items across the cross axis |
| `flex-wrap` | Allows items to move onto another line when they run out of room |
| `gap` | Adds space between items |
| `flex` | Sets how an item grows, shrinks and starts sizing along the main axis |

```css
.actions {
  display: flex;
  flex-wrap: wrap;
  justify-content: flex-end;
  align-items: center;
  gap: 0.75rem
}
```

With this row, I see the buttons pushed toward the end of the main axis and centered vertically within their line. On a narrow screen they can wrap. I keep the source order meaningful so the keyboard order follows the intended reading order.

## 5. Grid

I reach for Grid when I want rows and columns to share tracks, such as a set of workshop cards. I set the tracks on the container and let its direct children fill the cells in source order.

```css
.workshop-list {
  display: grid;
  grid-template-columns: repeat(3, minmax(0, 1fr));
  gap: 1rem
}
```

Here I create three equal columns. Grid subtracts the gaps before distributing the available space among the `1fr` tracks. `minmax(0, 1fr)` lets each track shrink below the default minimum implied by its content, so I still check long text and images for overflow. If I put the cards in a wrapped flex row, each row lays out its items independently. With Grid, the cards in different rows share the same column lines.

## 6. Responsive design and media queries

I start with a single column that fits a narrow viewport. I let the layout grow with the available room and add columns when the cards have enough space. I pick breakpoints by resizing the page and watching where the content starts to feel cramped.

I include this in the document's `head` so mobile browsers use the device-width layout viewport.

```html
<meta name="viewport" content="width=device-width, initial-scale=1">
```

I replace the fixed three-column example with these mobile-first rules.

```css
.page {
  max-inline-size: 70rem;
  margin-inline: auto;
  padding-inline: 1rem
}

img {
  max-inline-size: 100%;
  block-size: auto
}

.workshop-list {
  display: grid;
  gap: 1rem;
  grid-template-columns: minmax(0, 1fr)
}

@media (min-width: 40rem) {
  .workshop-list {
    grid-template-columns: repeat(2, minmax(0, 1fr))
  }
}

@media (min-width: 64rem) {
  .workshop-list {
    grid-template-columns: repeat(3, minmax(0, 1fr))
  }
}
```

Below `40rem` I get one column. At `40rem` the two-column rule applies. At `64rem` both queries match, and the later three-column rule wins because both selectors have the same specificity. The image can shrink with its container, and its height follows its aspect ratio.

I resize the viewport gradually and zoom in to check whether the content still fits. I look for horizontal scrolling, clipped labels and buttons that wrap awkwardly. Then I tab through the page again at a narrow width to check that the visual changes still make sense with the same keyboard order.

## 7. Components, props and composition

When I look at the workshop page, I split it where a piece has a clear job or appears in several places. I give the page responsibility for choosing what to show. I give the list responsibility for arranging workshops, and each card responsibility for showing one workshop.

```text
WorkshopsPage
├── SiteNav
└── WorkshopList
    ├── WorkshopCard
    │   └── SignupLink
    └── WorkshopCard
        └── SignupLink
```

I call the inputs a component receives from its parent **props**. For a workshop card, I can pass a title, a time and an action. I treat props as read-only inputs. If a workshop changes, the parent supplies the updated values.

I use **composition** when I build a larger piece out of smaller ones. For example, I can pass a signup link into the card on the listing page and a details link into the same card on the homepage. The card owns the layout, while the caller chooses the action. In plain JavaScript, I can express this by passing a DOM element as an input.

```javascript
function createWorkshopCard({ title, time, action }) {
  const card = document.createElement("article")
  const heading = document.createElement("h3")
  const schedule = document.createElement("p")

  heading.textContent = title
  schedule.textContent = time
  card.append(heading, schedule, action)

  return card
}

const signupLink = document.createElement("a")
signupLink.href = "/signup"
signupLink.textContent = "Sign up for HTML and CSS"

const card = createWorkshopCard({
  title: "HTML and CSS",
  time: "Saturday at 10:00",
  action: signupLink
})
```

I can append the returned card to the workshop list under its `h2`. For each card I create a fresh action element, since appending an existing DOM node moves it from its previous parent.

## 8. Data fetching and UI states

When I request `/api/workshops`, there is a gap between asking for the data and knowing the outcome. I model that as four states so the page can show something meaningful at every step.

| State | What I show |
| --- | --- |
| Loading | I tell the user that workshops are loading. |
| Success | I show the workshop list. |
| Empty | I explain that no workshops are available. For a filtered list, I can let the user clear the filters. |
| Error | I show a short error message and offer a way to retry. |

```text
Start request → Loading → Success with results
                        → Empty after a successful response
                        → Error if the request fails
```

I use a different message for an empty response and a failed request. An empty array confirms that the server returned a list with zero entries. A failure leaves me without a confirmed result.

```javascript
async function loadWorkshops(render) {
  render({ status: "loading" })

  let workshops

  try {
    const response = await fetch("/api/workshops")

    if (!response.ok) {
      throw new Error("Workshop request failed")
    }

    workshops = await response.json()
    if (!Array.isArray(workshops)) {
      throw new Error("Expected a workshop list")
    }
  } catch {
    render({ status: "error", retry: () => loadWorkshops(render) })
    return
  }

  if (workshops.length === 0) {
    render({ status: "empty" })
    return
  }

  render({ status: "success", workshops })
}
```

Here I pass in a `render` function that updates the page from the state. I check `response.ok` because HTTP errors such as `404` and `500` still give me a response from `fetch()`. I put loading and result messages in a status region, such as an element with `role="status"`, so updates can be announced without moving focus.

If I add filters that trigger another request, the earlier request can finish last. I cancel a superseded fetch with an `AbortController` or ignore its result, so an old response cannot replace the list for the current filter. [Fetch Standard](https://fetch.spec.whatwg.org/)

## 9. Client-side routing and browser history

I use routes to connect a URL to a view. For example, `/workshops` shows the list and `/workshops/42` shows one workshop. With client-side routing, clicking an internal link can change the URL and swap the view while keeping the current document loaded. The new view can still fetch data from the server.

| Browser API | How I use it |
| --- | --- |
| `history.pushState()` | I add a history entry when the user goes from the list to a detail page. |
| `history.replaceState()` | I update the current entry, for example to normalize the URL without adding an extra Back step. |
| `popstate` | I render the URL the browser has arrived at after Back or Forward in this app. |

```text
Open /workshops → click a workshop → /workshops/42
      ▲                                   │
      └── Back → popstate → render list ──┘
```

I render from `location.pathname` on the first load. When I intercept an ordinary click on an internal link, I call `pushState()` and render the new URL myself because `pushState()` does not fire `popstate`. When Back or Forward fires `popstate`, I render the current URL without adding another history entry.

I keep real `href` values so links can be copied or opened in a new tab. I let the browser handle external links, downloads and modified clicks such as Ctrl+click. When the view changes, I update the document title and make sure keyboard and screen-reader users can find the new main content.

If I paste `/workshops/42` into the address bar or reload it, the browser requests that path from the server. For a client-rendered app, I configure the host to serve the app's HTML for client-side routes while keeping API and static asset paths separate. Then the router reads the URL and displays the corresponding view. [HTML Standard history APIs](https://html.spec.whatwg.org/multipage/nav-history-apis.html#the-history-interface)
