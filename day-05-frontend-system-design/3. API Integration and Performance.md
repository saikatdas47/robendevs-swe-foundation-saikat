# API Integration and Performance

I continue with the workshop list from my earlier notes. I load public workshops, let a signed-in user book a seat and keep the page fast on a small screen.

## 1. REST and GraphQL from the client

With REST, I use a resource URL and an HTTP method. For example, I fetch the workshop list with `GET /api/workshops?limit=2&offset=0` and create a booking with `POST /api/bookings`. The server defines the response shape for each endpoint. If the workshop list omits instructor details, I can use another endpoint or ask the API to support an expanded response.

With GraphQL, I send an operation to an endpoint such as `/graphql`. I choose fields from the schema, including related fields such as the instructor's name. I choose REST when its resource endpoints already match what the page needs and I can reuse standard HTTP caching for public GET responses. I consider GraphQL when several views need different fields from the same related data. I still need the server to authorize access, enforce booking rules and resolve those fields efficiently.

### How I fetch workshops with GraphQL

I assume my practice API has a `workshops(first:, after:)` field and a `bookWorkshop(workshopId:)` mutation. These names and the connection shape come from this example schema. When I integrate with a real API, I check its schema for the supported fields and argument types.

```javascript
const workshopsQuery = `
  query Workshops($first: Int!, $after: String) {
    workshops(first: $first, after: $after) {
      nodes {
        id
        title
        availableSeats
        instructor {
          name
        }
      }
      pageInfo {
        endCursor
        hasNextPage
      }
    }
  }
`

async function graphql(query, variables) {
  const response = await fetch("/graphql", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ query, variables })
  })

  if (!response.ok) {
    throw new Error(`HTTP ${response.status}`)
  }

  const { data, errors } = await response.json()

  if (errors?.length || !data) {
    throw new Error("The GraphQL operation failed")
  }

  return data
}

async function fetchWorkshopPage(after = null) {
  const data = await graphql(workshopsQuery, { first: 2, after })
  return data.workshops
}
```

I pass values separately in `variables`. The `Int!` means `first` is required and cannot be null. The nullable `after` lets me send `null` for the first page. The response follows my selection, so I read `data.workshops.nodes[0].instructor.name` without requesting the instructor's full profile.

I check both the HTTP status and the GraphQL payload. GraphQL can return `errors` alongside partial `data`, even with HTTP 200. For this example I treat errors as a failed operation. On a read-only screen I could render partial data if the remaining fields are safe to use and the UI explains what could not load. [GraphQL response format](https://graphql.org/learn/response/)

## 2. Pagination

With offset pagination, I ask the REST endpoint for `limit=2&offset=0` and then `limit=2&offset=2`. I can jump to a known page by computing its offset. If a new item appears before the second page while I browse, the items can shift and I may see a duplicate or miss an entry.

With cursor pagination, I give the server the position it returned for the end of the last page. I treat that cursor as opaque and pass it back exactly as received. The API needs a stable ordering, and updates to the ordering fields can still move items. REST APIs can use cursors too. GraphQL connection fields typically expose the next position and whether more results exist through `pageInfo`. [GraphQL pagination](https://graphql.org/learn/pagination/)

If the first GraphQL response has workshop IDs `42` and `43`, plus `endCursor: "page-one-end"` and `hasNextPage: true`, my **Load more** click sends `{ first: 2, after: "page-one-end" }`. I append the next page to the existing list and hide the button when `hasNextPage` is false.

```javascript
const firstPage = await fetchWorkshopPage()
const workshops = [...firstPage.nodes]

if (firstPage.pageInfo.hasNextPage) {
  const nextPage = await fetchWorkshopPage(firstPage.pageInfo.endCursor)
  workshops.push(...nextPage.nodes)
}
```

I use the second call inside the click handler for a real Load more button. While it runs, I disable that button to prevent overlapping loads. If the user changes the filter, I reset the cursor and ignore any result for the old filter.

## 3. Optimistic booking

If a card shows three seats, I can show two immediately when the user clicks **Book**. I mark the booking pending and disable another click on that card. The server still decides whether the seat is available. On success I replace my estimate with the returned seat count. On failure I restore the previous value, show feedback and refresh availability when possible.

```javascript
const bookWorkshopMutation = `
  mutation BookWorkshop($workshopId: ID!) {
    bookWorkshop(workshopId: $workshopId) {
      booking {
        id
      }
      workshop {
        id
        availableSeats
      }
    }
  }
`

async function bookSeat(card, render) {
  if (card.pending || card.availableSeats < 1) return

  const previousSeats = card.availableSeats
  card.availableSeats -= 1
  card.pending = true
  card.error = ""
  render(card)

  try {
    const { bookWorkshop } = await graphql(bookWorkshopMutation, {
      workshopId: card.id
    })

    card.availableSeats = bookWorkshop.workshop.availableSeats
    card.bookingId = bookWorkshop.booking.id
  } catch {
    card.availableSeats = previousSeats
    card.error = "Could not confirm the booking. Check your bookings before trying again."
  } finally {
    card.pending = false
    render(card)
  }
}
```

I assume this API reports a rejected booking as a GraphQL error. If the API puts a business error such as `SOLD_OUT` inside the mutation payload, I check that field before accepting success. If the connection drops after I submit, the server may still have created the booking. I check the user's bookings before retrying, or use the API's idempotency mechanism if it offers one. The same pending, confirm and rollback steps also work with a REST request.

## 4. Image optimisation

I export the same workshop image at 480, 960 and 1440 pixels wide. I describe how wide the card will be in the layout so the browser can pick a suitable version for the viewport and display density. Here the card uses almost the full viewport on small screens and is 320 CSS pixels wide on larger screens.

```html
<img
  src="/images/workshop-480.webp"
  srcset="/images/workshop-480.webp 480w,
          /images/workshop-960.webp 960w,
          /images/workshop-1440.webp 1440w"
  sizes="(min-width: 48rem) 320px, calc(100vw - 2rem)"
  width="960"
  height="540"
  loading="lazy"
  alt="Participants working together at the workshop"
>
```

I keep the CSS slot width consistent with `sizes` and use matching aspect ratios across the versions. The width and height let the browser reserve space before the image loads. I compress the files and inspect how they look. I use lazy loading for cards below the fold. If the primary image is visible immediately and could be the Largest Contentful Paint element, I leave it eager so the browser can fetch it early. [Responsive images](https://web.dev/learn/images/descriptive/)

## 5. Caching and performance budgets

I cache a public image with a content hash in its filename for a long time. When I update the pixels, I publish a new URL. I can let public workshop data be cached briefly if the API allows some staleness. For a private booking list that should never be stored in an HTTP cache, I use `Cache-Control: no-store`. For GraphQL responses fetched with POST, I usually manage reuse in the client cache and refresh affected data after a mutation. A client cache and the browser's HTTP cache are separate places to look when I debug stale data.

I set budgets that I can measure for the public workshop list. These are example targets for this page.

| What I measure | Example budget |
| --- | --- |
| Initial JavaScript | At most 150 KB transferred after compression |
| Images loaded on the initial mobile view | At most 250 KB total transferred |
| Largest Contentful Paint | At most 2.5 seconds at the 75th percentile for real mobile visits |

For the transfer budgets, I use a cold-cache mobile run and compare the same page and conditions after each change. I use real-user mobile data for the LCP percentile. If a new card image pushes the initial image transfer over budget, I check its selected source, displayed size and compression before changing the budget. [Performance budgets](https://web.dev/articles/performance-budgets-101)
