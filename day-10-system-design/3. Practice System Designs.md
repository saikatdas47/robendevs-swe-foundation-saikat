# Practice System Designs

Each sketch starts with the main request, the data it needs, and a failure case. The numbers are examples for discussion.

## URL shortener

**Requirements.** Create a short link and redirect visitors. Support expiration and owner deletion. Assume reads greatly outnumber writes.

- `POST /links` validates the destination and creates a random Base62 code. Store the code under a unique constraint and retry a collision. Return the short URL.
- `GET /{code}` checks the mapping cache, reads the database on a miss, checks expiration, and returns a redirect. A temporary redirect makes changes easier to reflect because clients can cache permanent redirects for longer.
- Publish click events asynchronously so analytics delays do not slow redirects. Define what happens when the analytics queue is unavailable.
- On deletion, invalidate the mapping and any cached edge redirect. Test stale reads and protect link creation with rate limits.

The main table stores the code, destination, owner, and expiry. Test at the estimated peak and with a cold cache. Track redirect latency, misses, and creation conflicts.

## Rate limiter

**Requirements.** Allow each tenant an average of 100 requests per minute with a burst capacity of 20. Define whether traffic shares one budget across regions and which routes have separate limits.

- At the gateway, build the key from the authenticated tenant and endpoint group. Use a Redis token bucket with a capacity of 20 and a refill rate of about 1.67 tokens per second.
- Read the bucket, refill it using elapsed time, and consume one token in an atomic operation. An atomic update prevents several gateway instances from consuming the same token.
- When empty, return HTTP `429` and a useful `Retry-After` value. Expire idle bucket keys once a reset to a full bucket would be equivalent.
- Decide how each route behaves if Redis fails. A local emergency limit may keep low-risk traffic available. A strict route can reject requests until its shared limit is available.

Measure rejected requests by tenant and route. Test traffic at burst boundaries and calls arriving concurrently from several instances.

## Notification service

**Requirements.** Accept email and SMS requests, apply user preferences, and show delivery status. Assume providers can fail or return delayed callbacks.

1. Accept `POST /notifications` with an idempotency key. Store the request, recipient, channel, and initial status. Use an outbox entry to schedule it reliably.
2. Run separate channel workers. Check current preferences and provider limits. Send with a stable provider idempotency key when available.
3. Move through states such as queued, sent to provider, delivered, and failed. Verify callback signatures and make status updates idempotent. Accepting a send and confirming delivery are separate events.
4. Retry temporary errors with backoff. Keep permanent failures visible and use a dead-letter queue for jobs that need investigation.

A timeout after the provider accepted a message can cause duplicate sends. Reconcile using the provider reference before retrying when possible. Track queue age, delivery success, provider latency, and duplicate rates.

## Ride matching

**Requirements.** Match a rider to an available driver near the pickup point. Minimise wait time while preventing two active bookings for the same driver.

- Drivers publish location updates every few seconds. Store recent locations in a geospatial index. Expire stale driver positions and use recent heartbeats to determine availability.
- When a booking arrives, find nearby available drivers by location cell. Expand the search if few are available. Rank candidates by estimated pickup time and any agreed marketplace rules.
- Use a conditional update or transaction to reserve one driver for one ride. A short reservation deadline lets the system release a driver who does not accept.
- Persist booking and reservation states. Publish status changes for riders and drivers. Use an event version or sequence to avoid applying older updates after newer ones.
- Partition location work by city or region, allowing searches to cross nearby cell boundaries. Watch hot zones around large events.

Location can tolerate brief staleness. The actual driver reservation needs a stronger guarantee. Compare immediate dispatch with short batches. Batches can find better assignments at the cost of waiting to collect more requests.
