# Consistency, Transactions and Infrastructure

## Strong and eventual consistency

A strongly consistent read, in the linearizable sense, reflects completed writes in a single real-time order. For example, a driver reservation confirmed before a later read should appear in that read. Eventual consistency allows replicas or views to disagree temporarily. They should converge when writes stop and updates can reach them.

Use stronger guarantees for scarce inventory, payment decisions, or exclusive reservations. A sales dashboard or search index can often accept a short delay. Read-your-writes is a narrower promise. It means a client can read its own successful change even if other clients temporarily see older data.

### CAP and PACELC

During a network partition, a distributed system cannot guarantee both linearizable consistency and successful responses for every request to a working node. If two sides cannot communicate, accepting a write on both sides can leave conflicting values. Refusing a conflicting write can protect consistency while reducing availability for that operation. CAP availability has a formal meaning. It is different from a monthly uptime target. [Gilbert and Lynch on CAP](https://groups.csail.mit.edu/tds/papers/Gilbert/Brewer2.pdf)

**PACELC** adds the trade-off during normal operation. If there is a partition, choose how to trade availability against consistency. Else, consider the latency cost of coordinating replicas to get stronger consistency. For example, a write that waits for a remote quorum may take longer than writing locally and replicating afterwards. [Daniel Abadi on PACELC](https://www.cs.umd.edu/~abadi/papers/abadi-pacelc.pdf)

## Distributed transactions

A **saga** is a series of local transactions. Each service commits its own work. If a later step fails, compensating actions handle steps that already succeeded.

| Step | Action | Compensation if needed |
| --- | --- | --- |
| 1 | Create an order with pending status. | Mark the order cancelled. |
| 2 | Reserve stock. | Release the reservation. |
| 3 | Authorise payment. | Void the authorisation or start a refund if payment was captured. |
| 4 | Confirm the order. | Retry or reconcile if the final result is unknown. |

A compensation can fail and may need retries or manual review. Persist saga state and prevent steps from running twice. **Orchestration** uses a coordinator to decide the next step. **Choreography** lets services react to events, which can suit a short flow but gets harder to trace as dependencies grow.

### Outbox, inbox and idempotent consumers

1. Save the order and an outbox record in the same local database transaction. This closes the gap where the database write succeeds but the broker publish never happens.
2. Have a relay publish the outbox event and record its progress. If it crashes after publishing but before saving progress, the event can be published again.
3. In the consumer, start a transaction and insert the event ID into an inbox or processed-event table with a unique key for that consumer. Apply the business update only when that insert succeeds, and commit both together before acknowledging.
4. For external effects such as SMS, pass a stable idempotency key to the provider when supported. The inbox and database change alone cannot guarantee that an external request happens once.

Include the aggregate ID and version where order matters. An idempotent consumer can see the same event twice and leave the same business state after the second attempt.

## Service discovery, mesh and tracing

- **Service discovery** maps a stable service name to currently healthy endpoints. A registry-aware client can pick an instance, or the caller can send traffic to a stable name backed by a load balancer. Tests should cover stale endpoints and draining instances.
- **Service mesh** can apply service-to-service routing, mutual TLS, and telemetry through infrastructure near the services. It can simplify repeated network policy across teams, but adds a data path and configuration to operate. Business permissions still belong in application policy.
- **Distributed tracing** links spans across a request path. Propagate trace context across HTTP or message metadata and use separate spans for queue wait and processing where useful. A trace can show that a slow checkout was spending most of its time waiting for a payment service.

## Queueing, Little's Law and tail latency

When work arrives faster than it can be processed, a queue grows until traffic drops, enough capacity is added, or some traffic is rejected. Even below average capacity, bursty traffic and uneven service times create waiting. Latency can rise quickly as utilisation approaches saturation.

**Little's Law** says `L = λ × W` for a stable system over time. Use matching boundaries and units. At 200 completed requests per second and an average time of 0.15 seconds in the service, about 30 requests are in flight on average. If the mean wait in a queue is 0.05 seconds at the same throughput, the average queue contains about 10 requests. This gives an average and does not predict p99.

**p99 latency** is a threshold at or below which roughly 99% of requests finish. Tail latency matters when one request waits for several downstream calls. With 10 independent parallel calls, each having a 1% chance of exceeding a threshold, the chance that at least one exceeds it is about 9.6%. Real calls can be correlated, so validate with traces and load tests. Use deadlines, reduce unnecessary fan-out, and watch saturation rather than relying on average latency alone.
