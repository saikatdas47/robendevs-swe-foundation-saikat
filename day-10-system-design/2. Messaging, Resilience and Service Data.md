# Messaging, Resilience and Service Data

## Synchronous and asynchronous communication

A synchronous request waits for a response. Checkout may need an immediate answer from a payment authorisation API. Set a deadline and handle an unknown result because a timeout can occur after the payment provider has accepted the request.

An asynchronous message lets the caller hand off work. After an order commits, a worker can send an email later. A response such as HTTP `202 Accepted` can return a job ID and a status endpoint when completion matters. Queues absorb short bursts, but a lasting arrival rate above worker capacity grows the backlog.

A **command** asks a handler to do something, such as `SendReceipt`. An **event** describes something that happened, such as `OrderPaid`. Different consumers can react to the same event without the producer calling each of them.

## Queues and streams

A work queue typically distributes jobs among competing consumers. Acknowledgement tells the broker it can remove a delivery under the queue's rules. A stream keeps records for a retention period. Consumers track their position, and new consumers can replay retained history.

| Tool | Useful for | Ordering or delivery detail |
| --- | --- | --- |
| Apache Kafka | Durable event streams, replay, and independently consuming the same events in several applications. | Records are ordered within a partition. Key related events by order ID if their order matters. A consumer group shares partition work. |
| RabbitMQ | Work queues and routing messages to queues using exchanges. | Acknowledge after processing. Several consumers or redelivery can change effective processing order. RabbitMQ also has a Streams feature. |
| Amazon SQS | Managed AWS work queues with visibility timeouts. | Standard queues can redeliver and reorder. FIFO queues order within a message group. Consumer side effects still need safe retry handling. |
| Google Cloud Pub/Sub | Managed topics with multiple subscriptions, such as separate billing and reporting consumers. | Ordering is optional and uses ordering keys with publication from the same region for a given key. Handle redelivery. |
| Redis Streams | Retained streams with consumer groups when a Redis deployment already fits the workload. | Acknowledge processed entries, recover abandoned pending work, and choose retention and durability settings. |

Pick a tool based on replay, routing, retention, ordering scope, expected throughput, and operational ownership. Track oldest message age alongside queue depth. A fast-growing queue full of recent items and a small queue with hours-old items point to different problems. Route repeatedly failing deliveries to a dead-letter queue for investigation and safe reprocessing.

## Resilience

| Pattern | How it works | Checkout example |
| --- | --- | --- |
| Timeout | Bound the time a call can wait within the overall deadline. | Give a provider call part of the checkout deadline and pass the remaining time downstream. |
| Retry with backoff and jitter | Wait longer between retries and add a small random delay. Retry only eligible failures within a fixed budget. | Retry a transient provider error with the same idempotency key. Check the payment status when the result is uncertain. |
| Circuit breaker | Stop sending calls after repeated failures. After a cooldown, allow limited probes. Close the circuit when the dependency recovers. | Pause calls to an unavailable provider so checkout does not spend all its time waiting. |
| Bulkhead | Give workloads separate limits or resource pools. | Cap export workers separately so an export backlog cannot take every database connection needed by checkout. |

Apply retries in one intended layer where possible. Three attempts at each of three layers can turn one request into up to 27 downstream attempts. For sustained overload, limit incoming work or return a clear retry response. Keep a bounded queue and measure rejection, timeout, and recovery rates.

## Data ownership per service

The owning service manages writes to its data. Other services use its API, subscribe to its events, or maintain their own read model. Separate ownership can be enforced even when services use separate databases on the same managed server.

- **Replication** copies data for availability or read capacity. Replicas may lag. Send a read that must reflect a new write to the primary or wait for replay.
- **Partitioning** divides data by a key. Monthly partitions can simplify retention for events. Sharding by tenant can distribute writes across several databases. Watch for a hot tenant and plan how its data can move.
- **SQL or NoSQL** follows the workload. Orders and payments often need relational constraints and transactions. A document store can suit flexible catalogue items. A key-value store fits direct lookups, and a wide-column store can fit high-volume events with known partition queries.

A reporting service can build a view from order and payment events. The report may lag. It should display its freshness when users need to know how current the data is.
