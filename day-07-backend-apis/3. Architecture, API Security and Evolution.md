# Day 07 — Architecture, API Security and Evolution

I continue with the workshop API. I use the same booking rules whether the client calls a REST endpoint, sends a GraphQL operation or uses an internal gRPC client.

## 1. Modular, hexagonal and clean architecture

| Style | What I organise | How it looks in my API |
| --- | --- | --- |
| Modular | I organise code around features with explicit boundaries. | I have workshops, bookings and accounts modules. A caller goes through a module's public interface instead of accessing its tables directly. |
| Hexagonal | I put application logic behind ports and connect external systems through adapters. | Express and GraphQL are incoming adapters. A database repository and email queue are outgoing adapters. The booking use case works with a repository interface. |
| Clean | I arrange code so source dependencies point inward toward business rules. | My domain and use cases can run without importing Express, GraphQL or a database driver. Adapters depend on those inner rules and handle transport and storage details. |

```text
Incoming adapters                     Outgoing adapters
Express route ────┐                ┌── database repository
                 ├── BookSeat ─────┤
GraphQL resolver ─┘    use case     └── queue publisher
```

I can use all three ideas together. I start with feature modules inside one deployable backend. Inside bookings, I give the use case a small repository interface if I want to test its rules without a database or call it from multiple transports. I can supply an in-memory adapter in tests and a database adapter in production. I keep a rule like “take at most one remaining seat” in one place. If the rule needs an atomic database update, I make the repository contract express that guarantee.

These boundaries add interfaces and mapping code. In a small read-only module, I might keep a straightforward controller and repository. When logic starts to depend on several integrations, clear ports give me a place to separate those dependencies from the rules.

## 2. How I review API security

I use the OWASP API Security Top 10 (2023) to walk through the design.

| OWASP risk | What I check in my API |
| --- | --- |
| API1 Broken Object Level Authorization | I check whether this user can read or edit the specific booking ID. |
| API2 Broken Authentication | I validate credentials and token claims, protect sign-in and plan for expiry and revocation. |
| API3 Broken Object Property Level Authorization | I allowlist writable fields and only return properties the caller may read. |
| API4 Unrestricted Resource Consumption | I cap page size, request size, operation cost and expensive work per caller. |
| API5 Broken Function Level Authorization | I check who can run admin actions such as publishing a workshop. |
| API6 Unrestricted Access to Sensitive Business Flows | I protect booking and other scarce-resource flows against excessive automation. |
| API7 Server Side Request Forgery | I control destinations when backend code fetches a URL on the caller's behalf. |
| API8 Security Misconfiguration | I use safe TLS, CORS and error settings, and remove unused debug features. |
| API9 Improper Inventory Management | I track deployed hosts, API versions and routes so I can retire forgotten endpoints. |
| API10 Unsafe Consumption of APIs | I validate upstream responses and apply timeouts and size limits before relying on them. |

[OWASP API Security Top 10](https://owasp.org/API-Security/editions/2023/en/0x11-t10/)

**Injection.** I keep data separate from commands. For a PostgreSQL lookup, I pass the topic as a parameter with `db.query("SELECT id, title FROM workshops WHERE topic = $1", [topic])`. If the client provides a sort key, I map it to a fixed column name from an allowlist. I do the same in GraphQL resolvers because schema validation does not make string-built SQL safe.

**SSRF.** If my API imports workshop artwork, I prefer to choose the upstream service myself. If I must accept a URL, I restrict the schemes and destinations, enforce outbound network rules and prevent redirects to disallowed destinations. I account for DNS resolution and deny access to internal and link-local addresses. I cap download time and size too.

**Secrets.** I keep signing keys and database credentials in a secret manager and give each workload access only to what it needs. I inject secrets at runtime, keep them out of source, responses and logs, and plan how to rotate them. For a JWT signing key rotation, I plan how verifiers will accept still-valid tokens signed with the previous key during the transition.

**Zero trust.** I authenticate service calls and authorise actions even inside a private network. For example, the email worker can consume confirmation jobs but does not need permission to update workshop prices. I use workload identity, least privilege and auditable access decisions. [OWASP SQL injection prevention](https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.html) · [OWASP SSRF prevention](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html) · [NIST Zero Trust Architecture](https://csrc.nist.gov/pubs/sp/800/207/final)

## 3. REST, GraphQL and gRPC

| What I compare | REST | GraphQL | gRPC |
| --- | --- | --- | --- |
| How I call it | I send an HTTP method to a resource URL. | I send a typed query or mutation, commonly over HTTP, and select response fields. | I call a named RPC defined by a service contract. |
| How I describe the contract | I can publish OpenAPI for methods, paths and representations. | The schema describes fields, argument types and nullability. | I commonly use Protocol Buffers and generate client and server code. |
| What I choose it for | Public resource APIs where standard HTTP tooling and caching fit well | UI screens that need different shapes of related data | Internal service calls where generated clients and streaming are useful |

For REST I might use `GET /api/v1/workshops/42` and `POST /api/v1/bookings`. For gRPC I might define a service operation like this. I would usually use it for service-to-service calls. A browser integration generally needs a web-compatible client and endpoint, such as gRPC-Web.

```proto
syntax = "proto3";

service WorkshopService {
  rpc GetWorkshop(GetWorkshopRequest) returns (WorkshopReply);
}

message GetWorkshopRequest {
  string id = 1;
}

message WorkshopReply {
  string id = 1;
  string title = 2;
}
```

### How I build the GraphQL version

I save this as `graphql-demo.mjs` in a practice folder with the `graphql` package installed. I use the executor directly so I can see how schema, variables and resolvers work before adding an HTTP adapter. The in-memory data and identity stand in for my repository and verified JWT.

```javascript
import { buildSchema, graphql, GraphQLError } from "graphql"

const schema = buildSchema(`
  type Instructor {
    name: String!
  }

  type Workshop {
    id: ID!
    title: String!
    availableSeats: Int!
    instructor: Instructor!
  }

  type Booking {
    id: ID!
    workshop: Workshop!
  }

  type Query {
    workshop(id: ID!): Workshop
  }

  type Mutation {
    bookWorkshop(workshopId: ID!): Booking
  }
`)

const workshops = new Map([
  ["42", {
    id: "42",
    title: "Backend APIs",
    availableSeats: 3,
    instructor: { name: "Riya" }
  }]
])
const bookings = new Map()

function fail(message, code) {
  throw new GraphQLError(message, { extensions: { code } })
}

function bookSeat(user, workshopId) {
  if (!user) fail("Sign in to book", "UNAUTHENTICATED")

  const workshop = workshops.get(workshopId)
  if (!workshop) fail("Workshop not found", "NOT_FOUND")

  const key = JSON.stringify([user.id, workshopId])
  const existing = bookings.get(key)
  if (existing) return existing
  if (workshop.availableSeats === 0) fail("No seats left", "SOLD_OUT")

  workshop.availableSeats -= 1
  const booking = { id: `b${bookings.size + 1}`, workshop }
  bookings.set(key, booking)
  return booking
}

const rootValue = {
  workshop: ({ id }) => workshops.get(id) ?? null,
  bookWorkshop: ({ workshopId }, context) => bookSeat(context.user, workshopId)
}

const query = `
  query WorkshopDetails($id: ID!) {
    workshop(id: $id) {
      title
      availableSeats
      instructor { name }
    }
  }
`

const mutation = `
  mutation BookSeat($id: ID!) {
    bookWorkshop(workshopId: $id) {
      id
      workshop { id availableSeats }
    }
  }
`

function execute(source, variableValues, user = null) {
  return graphql({ schema, source, rootValue, variableValues, contextValue: { user } })
}

console.log(JSON.stringify(await execute(query, { id: "42" }), null, 2))
console.log(JSON.stringify(await execute(mutation, { id: "42" }, { id: "u7" }), null, 2))
```

The query returns the fields I selected and includes the nested instructor. For an unknown ID, the nullable `workshop` field returns `null`. After the mutation, I expect:

```json
{
  "data": {
    "bookWorkshop": {
      "id": "b1",
      "workshop": {
        "id": "42",
        "availableSeats": 2
      }
    }
  }
}
```

For an unauthenticated mutation, I get `data.bookWorkshop: null` and an `errors` entry with my `UNAUTHENTICATED` code. A response can contain both `data` and `errors` when a nullable field fails. The client checks the GraphQL payload even if the HTTP response is successful. In Express, I mount GraphQL on a route and build the context from verified JWT claims. The client sends the operation and variables. It does not supply the trusted identity in the context.

I keep the booking rule in the service. In this exercise a user can book a given workshop once. In production I enforce that unique booking and update the remaining seats atomically in the database. When listing workshops, resolving each instructor independently could cause one list query plus one query per row. I batch those lookups per request or fetch related data together. I also limit pagination and query cost, and check access before resolving private objects or fields. ## 4. API evolution and contract testing

I ask whether a currently working client would still work after my change. Removing a field, changing its type or introducing a new required input can break existing callers. Changing the meaning of a value can break them even if its type stays the same.

| API | How I evolve the contract |
| --- | --- |
| REST | I can add an optional field if consumers tolerate extra keys. I preserve existing meanings and use a new version for an incompatible change. |
| GraphQL | I can add a field such as `remainingSeats` while keeping `availableSeats` available. I mark the old field deprecated, then track actual use before removing it. I review nullability changes and new enum values against existing operations and generated clients. |
| gRPC and Protobuf | I preserve existing field numbers and use new numbers for added fields. If I remove a field, I reserve its number and name so they cannot be reused by mistake. |

To move the seat field in GraphQL, I add `remainingSeats` with the same value and put `@deprecated(reason: "Use remainingSeats")` on `availableSeats`. I update the clients and check their deployed operations before considering removal. During the transition, the old query should still receive the old field with the expected type and meaning.

I check compatibility in CI at two levels. First I diff the OpenAPI document, GraphQL schema or Protobuf definition against the released contract. Then I verify representative consumer interactions against the provider. For this app, I keep the old WorkshopDetails query as a fixture. I check that it returns three available seats for the seeded record, that booking changes the count to two and that a retry by the same user does not decrement it again. That catches a change in behaviour a schema diff cannot see.
