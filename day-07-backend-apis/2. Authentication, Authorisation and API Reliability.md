# Day 07 — Authentication, Authorisation and API Reliability

I continue with the workshop API. A user signs in, edits a workshop if they have permission and books a seat. Once the booking is saved, an email can go out in the background.

## 1. Sessions, tokens and password hashing

**Authentication** tells me who is making the request. **Authorisation** tells me whether that person can perform the requested action.

| Sign-in approach | How I recognise later requests | What I manage |
| --- | --- | --- |
| Server-side session | The browser sends a cookie with an opaque session ID. I look it up in the session store. | I can revoke the session in the store. If I run several API instances, they need access to the same session state. |
| Access token | The client sends a bearer token. I verify a signed token such as a JWT or look up an opaque token. | I set an expiry and decide how refresh and revocation work. A verified JWT can be accepted without a per-request session lookup, but early revocation needs another mechanism. |

Cookies and tokens solve different parts of the problem. A cookie is a way the browser carries a value and can carry either a session ID or a token. With a session cookie I use `HttpOnly`, `Secure` and an appropriate `SameSite` policy, and protect state-changing requests against CSRF. I rotate the session ID when sign-in succeeds and invalidate it on logout.

When I store passwords, I use a password hashing function such as Argon2id with a unique salt and a suitable work factor. I store the encoded hash and use the library to verify a submitted password against it. I never store the original password. A fast general-purpose hash such as SHA-256 is unsuitable on its own because it makes guesses cheap.

```javascript
import argon2 from "argon2"

export async function hashPassword(password) {
  return argon2.hash(password, { type: argon2.argon2id })
}

export async function verifyPassword(storedHash, submittedPassword) {
  return argon2.verify(storedHash, submittedPassword)
}
```

This Node.js snippet uses the `argon2` package. When I wire it into sign-in, I rate limit attempts and use the same public failure message for invalid credentials. [OWASP password storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) · [OWASP session management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)

## 2. JWT, OAuth 2.0 and OpenID Connect

| Term | How I use it |
| --- | --- |
| JWT | A token format that can carry claims such as subject and expiry. In the previous Express example I verify the signature, algorithm, issuer, audience and expiry before trusting claims. A signed payload is readable, so I keep secrets out of it. |
| OAuth 2.0 | A protocol framework for granting a client access to an API. I use the access token at the API. The token can be opaque or a JWT. |
| OpenID Connect (OIDC) | An identity layer on top of OAuth 2.0. I use a validated ID token at the client to establish who signed in. I use an access token intended for my API when calling it. |

For external sign-in, I use an OIDC client library. I redirect the browser to the identity provider with Authorization Code and PKCE. The provider returns a code to the registered callback and the client exchanges it for tokens. The library checks the response, including state and ID-token validation such as issuer, audience and nonce when used. My API checks that the access token is intended for it and has the required permission. A bearer token can be used by whoever obtains it, so I send it over HTTPS and keep it out of logs. [OAuth security best current practice](https://www.rfc-editor.org/rfc/rfc9700.html) · [OpenID Connect Core](https://openid.net/specs/openid-connect-core-1_0.html)

## 3. RBAC, ABAC and object-level authorisation

With **RBAC**, I assign permissions through roles. An editor can attempt to edit a workshop, while a viewer cannot. With **ABAC**, I evaluate attributes about the user, the resource and sometimes the request. I can require an editor's organisation to match the workshop's organisation.

I still check the specific object. If an editor can update only workshops they own, being an editor does not grant access to every workshop ID.

```javascript
export function canEditWorkshop(user, workshop) {
  return user.role === "editor" &&
    user.organisationId === workshop.organisationId &&
    user.id === workshop.ownerId
}
```

After authentication, I load the workshop and run that policy in the service before changing it. I get the user identity from verified credentials and the workshop attributes from storage. For example, editor `u7` can update their own workshop but cannot update workshop 42 by changing the URL if 42 belongs to `u8`. I apply the check on every applicable endpoint. I use `401` for missing or invalid credentials and can return `403` for a denied action, or `404` when the API deliberately hides whether a record exists. [OWASP API object-level authorisation](https://owasp.org/API-Security/editions/2023/en/0xa1-broken-object-level-authorization/)

## 4. Describing my API with OpenAPI

I describe the method, path, authentication, input and possible responses so someone can call the API without reading my Express code. This example defines a booking endpoint that returns `201` when the booking has been saved. The confirmation email is separate work.

```yaml
openapi: 3.1.0
info:
  title: Workshop API
  version: 1.0.0
paths:
  /api/v1/bookings:
    post:
      operationId: createBooking
      security:
        - bearerAuth: []
      parameters:
        - name: Idempotency-Key
          in: header
          required: true
          schema:
            type: string
            minLength: 1
            maxLength: 128
      requestBody:
        required: true
        content:
          application/json:
            schema:
              type: object
              required: [workshopId]
              additionalProperties: false
              properties:
                workshopId:
                  type: integer
                  minimum: 1
      responses:
        "201":
          description: Booking created
          headers:
            Location:
              schema:
                type: string
          content:
            application/json:
              schema:
                type: object
                required: [id, workshopId]
                properties:
                  id:
                    type: string
                  workshopId:
                    type: integer
        default:
          description: Error response
          content:
            application/json:
              schema:
                $ref: "#/components/schemas/ApiError"
components:
  securitySchemes:
    bearerAuth:
      type: http
      scheme: bearer
      bearerFormat: JWT
  schemas:
    ApiError:
      type: object
      required: [error]
      properties:
        error:
          type: object
          required: [code, message]
          properties:
            code:
              type: string
            message:
              type: string
```

For my full API contract I list expected error statuses explicitly and include examples, such as `409` when a workshop sells out or a key is reused with a different request. I keep the spec and implementation in sync with contract checks. Describing bearer auth in the spec does not enforce it. My Express middleware still verifies the credentials. [OpenAPI specification](https://spec.openapis.org/oas/v3.1.0)

## 5. Middleware for logging, request IDs, tracing and rate limiting

```text
Request → correlation ID and trace → unauthenticated limits
        → verify credentials → account limits where needed
        → controller → service → response log
```

I add a request ID early and return it to the caller. I log the route template, status and duration so I can look up a failure without logging passwords, bearer tokens or the full body.

```javascript
import { randomUUID } from "node:crypto"

export function logRequest(req, res, next) {
  const requestId = randomUUID()
  const start = performance.now()

  res.locals.requestId = requestId
  res.set("X-Request-Id", requestId)

  res.on("finish", () => {
    console.info(JSON.stringify({
      requestId,
      method: req.method,
      route: req.route ? `${req.baseUrl}${req.route.path}` : "unmatched",
      status: res.statusCode,
      durationMs: Math.round(performance.now() - start)
    }))
  })

  next()
}
```

I mount this with `app.use(logRequest)` before my routes. For work that crosses services, I use tracing instrumentation such as OpenTelemetry. One trace ID connects the spans for the incoming request, database call and downstream API call. I use a standard propagation header such as `traceparent`. The request ID helps me find a log for one HTTP request, while the trace shows where time went across the services.

I can limit unauthenticated traffic by IP at the edge and apply a per-account limit after authentication. For several API instances I use a shared limiter store or a gateway so the limit applies across instances. I only trust forwarded client IP information from configured proxies. When a caller exceeds a limit, I return `429` and a `Retry-After` header when I can provide a useful delay. [W3C Trace Context](https://www.w3.org/TR/trace-context/) · [Express behind proxies](https://expressjs.com/en/guide/behind-proxies.html)

## 6. Idempotency keys and safe retries

I click Book and the server saves booking `b42`, but the connection drops before I receive the response. I retry the same request with the same idempotency key so the server can return the saved result instead of taking another seat.

1. I scope the key to the authenticated user and operation. I store a fingerprint of the request so the same key cannot silently apply to a different workshop.
2. I use a unique constraint or another atomic mechanism so concurrent requests with the same key cannot both create a booking. I commit the booking and saved outcome together when they share a database.
3. I return the original result for a matching completed request. For a matching request still in progress, I give the caller an explicit way to retry later. If the payload differs, I return a conflict.
4. I document how long I retain the key. The same key is for retries of one attempt. A new intentional booking uses a new key.

I retry transient failures with a small attempt limit, exponential backoff and jitter. If the API returns `Retry-After`, I respect it within my overall deadline. I can usually retry a read such as GET after a transient failure. For a POST that creates a record, I first check whether the API makes retries safe. A timeout tells me I did not see the outcome, so I keep the same key when retrying a supported write. [HTTP idempotent methods](https://www.rfc-editor.org/rfc/rfc9110.html#name-idempotent-methods)

## 7. Background jobs and queues

Once I save a booking, I can return `201` and let a worker send the confirmation email. If the whole requested operation has only been accepted for later processing, I can return `202` and give the client a job status URL.

```text
POST booking → database transaction saves booking and outbox event → 201
                                     │
                                     ▼
                          outbox relay → queue → email worker
```

I use an outbox when the booking and the instruction to send the email must survive the same database commit. An outbox relay publishes that event to the queue. If the relay publishes twice or the queue redelivers, the worker uses the stable event ID and a deduplication mechanism. For sending an email, I use a provider idempotency key if available because a worker can crash after sending and before recording success.

I acknowledge the job after handling it. Temporary failures can retry with backoff. After the retry limit, I send the job to a dead-letter queue or record it for review. I monitor how long jobs wait, how often they fail and how many are retried. A successful booking can stay valid even while its confirmation email is delayed.
