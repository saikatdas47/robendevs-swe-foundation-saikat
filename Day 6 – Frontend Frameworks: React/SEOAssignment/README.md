# Little Market — React Product Listing Assignment

A beginner-friendly, mobile-style product catalog using React, Vite, JavaScript, plain CSS, React Router and DummyJSON. No account or API key is required.

No reference screenshots were supplied in the chat or workspace. This implementation uses a minimal white/gray design, a two-column grid, and the same 480px maximum width on both routes. Matching a particular screenshot requires that reference.

## Setup and run

Use Node.js 22.12+ (or a compatible newer version) and npm. From this existing project:

```bash
cd /home/saikat/Desktop/SEOAssignment
npm install
npm run dev
```

Open the local URL printed by Vite, normally http://localhost:5173. To install the exact versions recorded in package-lock.json on another machine, use `npm ci` instead of `npm install`.

Build and inspect production output:

```bash
npm run build
npm run preview
```

Open http://localhost:4173. `preview` is for local inspection, not a production server. Deploy the `dist` folder to a static host, with an SPA fallback: requests such as `/products/1` must serve `index.html`. Otherwise refreshing a detail URL can return a server 404. No environment variables or backend setup are needed.

## Architecture and request flow

```mermaid
flowchart TD
  A[index.html + main.jsx] --> B[App + BrowserRouter]
  B -->|/| C[ProductList]
  C --> D[loadMore + request guard]
  D --> E[api.js: getProducts]
  E --> F[Fetch page: limit=10, skip=N]
  E --> G[Fetch page: limit=10, skip=N+10]
  F --> H[Both succeed: combine + deduplicate IDs]
  G --> H
  H --> I[Render ProductCards]
  I --> J[Bottom sentinel + IntersectionObserver]
  J -->|More available| D
  I -->|Click Link| K[/products/:id]
  B --> K
  K --> L[Lazy-load ProductDetail]
  L --> M[api.js: getProduct]
  M --> N[GET /products/:id]
  N --> O[Detail view]
  O -->|Back to collection| C
```

বাংলায়: browser React app চালায় → list page দুটি request পাঠায় → response থেকে card বানায় → নিচে scroll করলে পরের দুটি request যায়। Product click করলে URL বদলায় এবং ওই product-এর আলাদা API call হয়।

### API functions

- `fetchJson(url, signal)`: awaits `fetch`, checks `response.ok`, throws a readable error for failure, then returns parsed JSON. Fetch does not automatically throw for HTTP 404/500, so this explicit check matters.
- `getProducts(skip, signal)`: builds the list URL using `BATCH_SIZE = 10`, the requested offset and `select` to reduce the returned fields. Returns the promise from `fetchJson`.
- `getProduct(id, signal)`: encodes the route ID and requests `/products/:id`. Detail pages need the full product response.
- `formatPrice(price)`: formats a numeric USD price with `Intl.NumberFormat`.

`signal` connects the request to an `AbortController`; calling `abort()` cancels work no longer needed. কোনো page ছাড়লে তার pending request cancel করা হয়।

### React state vs refs in the list

`useState` values cause UI updates: `products`, `loading`, `error`, `hasMore`, `total`.

`useRef` values persist between renders without causing a render:

- `nextSkip`: the next offset, starting at zero.
- `busy`: immediate lock against repeated observer events/button calls.
- `finished`: immediate guard when all results are consumed.
- `controller`: the current cancelable request cycle.
- `sentinel`: the DOM element observed near the bottom.

`loadMore()` is wrapped in `useCallback` so effects can depend on a stable function. It checks the guards, sets loading, starts two requests, combines successful results, removes duplicate IDs with a `Set`, advances the offset and updates the end state. `catch` shows an error and cancels the other in-flight request; `finally` releases the lock. The state updater receives `previous` so it appends to the latest list.

The first `useEffect` sets the title, starts the initial cycle and returns an unmount cleanup. The second effect installs `IntersectionObserver`. Its callback checks `entries[0].isIntersecting`, then calls `loadMore()`. Cleanup disconnects the observer. It reconnects after successful loading, which also handles a viewport tall enough to need another cycle immediately. During an error it stays disconnected so it cannot create an automatic retry loop.

The card's `map` creates one component per product. The updater's `filter` checks every new ID against previously seen IDs, including other items in the same cycle. The image's error callback switches to text. Detail's retry callback increments `attempt`, rerunning its effect. These small inline callbacks do not need separate utility files.

## Infinite scroll, limit, skip and two-page cycles

`limit` = সর্বোচ্চ কতগুলো product চাই। `skip` = শুরু থেকে কতগুলো product বাদ দিতে হবে। These are API offsets, not visible page buttons.

With batch size 10:

| Loading cycle | Request A | Request B | Normally appended |
| --- | --- | --- | --- |
| 1 | `limit=10&skip=0` | `limit=10&skip=10` | First 20 products |
| 2 | `limit=10&skip=20` | `limit=10&skip=30` | Next 20 products |
| 3 | `limit=10&skip=40` | `limit=10&skip=50` | Next 20 products |

Both requests start together with `Promise.all`. This is two pages of API data per cycle, displayed as one continuous grid. There is no numbered pagination UI.

1. Initial mount calls `loadMore()`.
2. `busy.current = true` happens synchronously before awaiting the network, preventing overlapping cycles.
3. The requests use offsets `N` and `N + 10`.
4. Only after BOTH succeed do we commit their results. Response order stays correct even if request B finishes first.
5. Existing and incoming IDs are deduplicated.
6. `nextSkip` advances by `2 × 10 = 20`. It counts API positions, not unique cards, so duplicates cannot shift the offset backwards.
7. `nextSkip >= total` ends loading. Two empty pages also stop loading defensively.
8. A sentinel within 300px of the viewport triggers another cycle. `rootMargin: '300px'` starts loading slightly before the user reaches the bottom.
9. On failure, skip does not advance; the retry button repeats the same pair. Products from earlier cycles stay visible.
10. The final pair may include a short or empty second batch. Example: total 25 → cycle 1 gives 20; cycle 2 requests skip 20 and 30, gives 5 plus 0, then ends with 25 unique cards. Total is read from the API, never hardcoded.

The “Load more” button is an accessible manual alternative and a fallback for browsers without IntersectionObserver. Normal scrolling triggers loading automatically. Loading text and end-of-results text are announced politely; errors use an alert.

This implementation assumes the API dataset remains stable while browsing. Removing duplicate IDs protects the display, but offset pagination cannot guarantee no missed items if a live database reorders or inserts items between requests. Returning to the list remounts it and starts from its first cycle; this small assignment deliberately does not persist its full list or scroll position.

## CSR vs SSR

**This application uses client-side rendering (CSR).** The static server sends `index.html`, CSS and JavaScript. The browser runs React, sends API requests from effects and builds product UI. The Vite development server and production preview server serve files; they do not render product HTML on the server.

```text
CSR: browser gets HTML shell → downloads/runs JS → fetches API → renders products
SSR: server fetches data → renders product HTML → browser receives HTML → hydrates
```

`async/await` only makes asynchronous code easier to read. It does NOT enable SSR. SSR requires server-side React rendering and a server data-loading strategy, followed by browser hydration. For example, React offers `renderToPipeableStream` on Node.js. That is a different architecture, not implemented in this project.

CSR keeps this assignment simple. Its product content depends on JavaScript and API availability. Some crawlers execute JavaScript, others may not; social preview bots may only see the generic HTML metadata. Client-side titles are updated, but this is not a complete product SEO strategy. SSR or prerendering can supply per-product HTML and metadata earlier. Infinite scrolling alone also does not expose every deep item as an initially present link; production search discovery could use crawlable category pages and a sitemap. A good Lighthouse SEO score does not prove complete indexing.

## Performance choices and their limits

- **LCP:** the first card image and detail hero use `loading="eager"` with `fetchPriority="high"`. Other card images use native lazy loading. API/CDN preconnect hints help connection setup. The likely LCP element must still be checked in DevTools: it could be the heading instead of an image. CSR data fetching still delays image discovery.
- **CLS:** image containers reserve square space with `aspect-ratio`; images declare width and height. Two-line card titles reserve a consistent minimum height. No external fonts. Appending results can still move the bottom controls, so measure actual shifts.
- **INP:** IntersectionObserver avoids continuous custom scroll handlers; only two small API batches are processed per cycle. No heavy filtering, UI framework or Redux. Every product remains in the DOM; exceptionally large catalogs may eventually need virtualization, which is intentionally omitted here.
- **Payload:** the list requests only required fields, thumbnails are used for cards, and the detail page has its own JavaScript chunk. Lazy routing defers the detail code, not the entire React runtime.
- **Accessibility:** semantic header/main elements, real links/buttons, image alternatives, skip link, visible focus, readable loading/error states and responsive widths.

These are implementation choices, not measured guarantees. Remote API latency, image sizes, device CPU and network quality affect the result.

## Chrome DevTools and Lighthouse testing

Use the **production preview**, not the development server, for representative audit runs:

```bash
npm run build
npm run preview
```

1. Open http://localhost:4173 in Chrome, preferably a fresh Incognito window with extensions disabled.
2. Open DevTools (F12 or Ctrl+Shift+I). Select **Lighthouse** (possibly under the `»` menu).
3. Select navigation/page-load mode, **Mobile**, and **Performance, Accessibility, Best Practices, SEO**.
4. Run **Analyze page load / Run audit** (wording depends on Chrome version).
5. Read failed audits and diagnostics. Export the HTML/JSON report. Record Chrome version, device/network settings, route and date alongside any real scores.
6. Repeat for a direct detail URL such as http://localhost:4173/products/1. Run a few times under the same conditions and compare representative results; network variability matters.
7. Check Accessibility manually too: Tab through cards/buttons, follow links with Enter, test the skip link and inspect screen-reader announcements.

**Do not treat Lighthouse's lab performance score as real-user INP.** In DevTools' **Performance** panel, record a session while scrolling, clicking cards and using back navigation; inspect interactions and long tasks. A page-load audit commonly reports Total Blocking Time as a lab responsiveness signal; actual field INP requires real user interaction measurements. Inspect LCP and layout shifts in the Performance trace. Lighthouse scores are diagnostic snapshots, not guaranteed grades.

### Functional test checklist

Use DevTools **Network → Fetch/XHR**, enable Preserve log where useful, and use Slow 3G/4G to expose races:

- Fresh list: see `skip=0` and `skip=10`, both `limit=10`; 20 unique cards after success (unless total is smaller).
- Scroll close to the bottom: see `skip=20` and `skip=30`. Continue and inspect increasing offsets. No repeated in-flight pair when scrolling rapidly.
- Click a card: URL becomes `/products/ID`, a separate `/products/ID` request appears, and matching details render.
- Refresh a detail URL and test `/products/999999`: valid details or a useful not-found error, never a blank page.
- Use “Back to collection” and browser Back/Forward. New list mounts load again by design.
- Use Network request blocking for `*dummyjson.com/products*` (rather than browser-wide Offline, which can block the local app too): list error should show “Try again”. Disable blocking and retry. For an error after successful cycles, old cards remain and skip is retried unchanged.
- Navigate away before a slow request finishes: pending request should cancel rather than paint the wrong route.
- Block `*cdn.dummyjson.com*` to verify the image fallback and stable image area.
- Scroll through the actual total: the final message appears and no further API cycle starts. Inspect duplicate product link URLs with the Elements panel if needed.
- In device toolbar, test 320, 375, 390 and 480px widths, then desktop. The shell stays at most 480px and should not horizontally overflow.
- Disable JavaScript and reload: only the HTML shell remains. This confirms the CSR limitation.
