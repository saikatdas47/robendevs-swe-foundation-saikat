# Team Review and Testing

## Definition of Ready and Definition of Done

| Agreement | Question | Example |
| --- | --- | --- |
| Definition of Ready | Is there enough detail to start this work? | The user outcome, acceptance checks, dependencies, and biggest unresolved risks are clear. |
| Definition of Done | Does the Increment meet the agreed quality standard? | Required tests and review pass, docs and operational checks are updated when needed, and the change is ready to release. |

Definition of Ready is an optional team agreement. Acceptance criteria apply to one item. Definition of Done sets a common quality standard for the Increment. An export story may satisfy its CSV requirements and still need tenant isolation tests to meet that standard.

## Pull requests and code review

Keep the change small enough to review. Explain the user impact and identify risky parts such as a schema change or permission check. Reviewers should read the linked requirement, check the important paths, and give specific feedback.

Review for correctness, tenant and data boundaries, failure handling, and missing tests. Separate blocking problems from optional improvements. For example, ask for a test proving that a worker cannot export another shop's orders. Suggest a clearer helper name as a separate, optional comment when the existing name is understandable.

A PR template can prompt for information that helps the reviewer. This example can be copied into the team's template.

```markdown
## Purpose
Link the work item and describe the user impact.

## Changes
List the main changes and any migration or API impact.

## Verification
List the checks run and their results.

## Rollout and recovery
Describe flags, monitoring, and how to recover if needed.
```

## The testing pyramid

Use many fast tests for small units, fewer integration tests for boundaries, and a focused set of end-to-end tests for important journeys. The exact mix should follow the risk and cost of each test. Contract tests help when interfaces change across separately deployed services.

| Test type | What it checks | Order export example |
| --- | --- | --- |
| Unit | A small rule or function in isolation. | A date range validator rejects an end date earlier than the start date. |
| Integration | Components work together with a real boundary such as a database or queue. | The API creates an export record and outbox entry in the same database transaction. |
| End-to-end | A whole workflow through the main entry point. | Staff requests an export, waits for it, and downloads the CSV in the browser. |
| Contract | An API or event still meets the expectations shared between consumer and provider. | The worker receives an event with the promised export ID, tenant ID, and schema version. |

An integration test can cover a tenant boundary with two rows that share the same local order number across shops. An end-to-end test can cover the successful download and one permission failure. Add cases for empty exports, retries, and expired download links where the requirements call for them. Keep test data repeatable and inspect the precise result that matters.
