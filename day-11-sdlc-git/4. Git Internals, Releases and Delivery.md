# Git Internals, Releases and Delivery

## Objects, refs and HEAD

Git stores objects by content ID. A **blob** holds file contents. A **tree** maps filenames to blobs or subtrees. A **commit** points to a root tree and records parents and metadata. An annotated **tag** is a tag object with its own metadata that points to another object.

A **ref** names an object. Branch refs move when new commits are added. Tag refs normally mark a stable point. `HEAD` usually points to the current branch. In detached HEAD, it points directly to a commit. Create a branch before leaving detached work that needs a durable name. The index is the staging area for the next commit.

```bash
git cat-file -t HEAD
git cat-file -p HEAD
git show-ref --heads
git reflog --date=relative
```

The **reflog** is a local record of recent ref changes. If a local branch moved unexpectedly, find the old commit and create a recovery branch with `git branch recovery <commit>`. Reflog entries can expire and reflogs are local to the repository.

## Find a regression with bisect

Git bisect searches between a known good commit and a known bad commit. Use a stable test that passes before the regression and fails after it.

```bash
git bisect start
git bisect bad HEAD
# Set GOOD_COMMIT to a tested good commit ID first.
git bisect good "${GOOD_COMMIT:?Set GOOD_COMMIT to a known good commit ID}"
# Run the test at the commit Git checks out.
# Mark each result with git bisect good or git bisect bad.
# Use git bisect skip if a commit cannot be tested.
git bisect reset
```

Set `GOOD_COMMIT` to a real commit ID before running the example. Run the final reset after Git reports the result. With an automated check, `git bisect run <command>` can drive the search. The command should exit with 0 for good, 125 to skip, or an appropriate nonzero status for bad. [Git bisect documentation](https://git-scm.com/docs/git-bisect)

## Releases and branch protection

**Semantic Versioning** uses `MAJOR.MINOR.PATCH` for a declared public API after version 1.0.0. A compatible fix goes from 1.4.2 to 1.4.3. A compatible new feature goes to 1.5.0. A breaking API change goes to 2.0.0. A prerelease such as `2.0.0-rc.1` can identify an early build. [Semantic Versioning specification](https://semver.org/)

Release notes explain changes in terms the audience can use. Include changes and fixes, breaking changes with upgrade steps, and known issues when relevant. Tag the release commit, record the deployed version, and link the notes to that version.

Branch protection or a ruleset can require pull requests, approvals, and passing status checks before a merge. It can also restrict force pushes and deletion. Use a clear policy for emergency changes and record any bypass. [GitHub protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)

## Engineering records

| Record | What to capture | Example |
| --- | --- | --- |
| Architecture Decision Record (ADR) | Status, context, options, decision, and consequences. | Run large exports in background jobs. This frees API capacity and adds job status and retry handling. |
| Incident review or RCA | Impact, timeline, contributing causes, detection, recovery, and follow-up owners. | Export jobs used the same connection pool as checkout. Separate limits and add an alert on connection wait. |

Treat an incident review as a way to improve the system and how it is operated. Record what helped and what made recovery harder. Give each follow-up an owner and a completion check.

### DORA metrics

| Metric | What it measures |
| --- | --- |
| Change lead time | Time from a committed change to production deployment. |
| Deployment frequency | How often changes deploy to production. |
| Failed deployment recovery time | Time to recover after a deployment that requires immediate intervention. |
| Change fail rate | Share of deployments that require immediate intervention. |
| Deployment rework rate | Share of deployments driven by unplanned work to address a production incident. |

Measure trends for one service or team over time. If lead time rises, check review wait, CI time, and release scheduling before guessing at the cause. Avoid using these metrics as individual targets. [DORA software delivery metrics](https://dora.dev/guides/dora-metrics/)

## Feature flags and progressive delivery

A deployment puts code into an environment. A release exposes behaviour to users. A **feature flag** can keep an export feature off until it is ready to release. Use a stable cohort, an owner, and a removal date. Enforce authorisation separately because a flag only controls feature availability.

For a progressive rollout, enable the feature internally, then for a small merchant cohort, then for more tenants if measurements stay healthy. Compare export success, job age, and checkout errors with a baseline. Pause or disable the feature if it harms production. Plan database changes so old and new application versions can overlap. A flag cannot undo data that was already written.

## Secure SDLC

| Stage | Example control |
| --- | --- |
| Requirements and design | Identify tenant boundaries, sensitive fields, permissions, and abuse cases. |
| Build and review | Use parameterised queries, scoped access, dependency review, and secret scanning. |
| CI and release | Run relevant checks, protect build credentials, and limit who can approve and deploy. |
| Operation | Monitor failures and security events, patch dependencies, and verify restore and incident procedures. |

For exports, verify access when creating the job and when downloading the result. Give the link a short lifetime and record access in an audit trail. Test that an expired link and a request from another tenant are both rejected.
