# Day 06 — React Hooks in Practice

I use my workshop page to revise this. I type a search, clear it, change a filter and open the saved workshops view. Each action helps me remember what React should keep between renders and what I can calculate again.

| When I need to… | What I reach for |
| --- | --- |
| Keep a value that affects what I see | `useState` |
| Keep React in sync with a browser API, connection or other external system | `useEffect` |
| Reach a DOM element or hold a value that can change without a render | `useRef` |
| Reuse the result of an expensive calculation while its inputs stay the same | `useMemo` |
| Update related state through named actions | `useReducer` |
| Read a value supplied to a whole subtree | Context with `useContext` |
| Reuse logic that calls Hooks | A custom Hook |

I call these Hooks at the top level of a function component or another Hook, before any early return. I put a condition inside an Effect or a handler when I need one. React relies on the same call order across renders. [Rules of Hooks](https://react.dev/reference/rules/rules-of-hooks)

## 1. useState — I remember a value the UI uses

```jsx
import { useState } from "react"

export function SeatPicker() {
  const [quantity, setQuantity] = useState(1)

  function addTwoSeats() {
    setQuantity((previous) => previous + 1)
    setQuantity((previous) => previous + 1)
  }

  return (
    <button type="button" onClick={addTwoSeats}>
      Add two seats · selected {quantity}
    </button>
  )
}
```

I start with one seat. On the first click, the first updater changes `1` to `2` and the second changes `2` to `3`. If I call `setQuantity(quantity + 1)` twice in that handler, both calls request the same value, `2`. The handler keeps seeing the snapshot from the render that created it, even immediately after a setter call.

For an object, I create a new value. If I only change one filter, I can write `setFilters((previous) => ({ ...previous, soldOut: true }))`. For a nested change, I copy the nested part too. I let React keep any related UI in sync on the next render. I read the initial argument as the starting value for the mount. If producing it is expensive, I pass a pure initializer function, such as `useState(readInitialFilters)`. [React useState](https://react.dev/reference/react/useState)

## 2. useEffect — I connect React to something outside it

Imagine every workshop has a live seat counter. I pass in a `subscribe` function that accepts a workshop ID and a callback, and returns a function that unsubscribes. I keep the supplied `subscribe` function stable across renders while it represents the same service.

```jsx
import { useEffect, useState } from "react"

function SeatUpdates({ workshopId, subscribe }) {
  const [seats, setSeats] = useState(null)

  useEffect(() => {
    const unsubscribe = subscribe(workshopId, setSeats)
    return unsubscribe
  }, [workshopId, subscribe])

  return <p>{seats === null ? "Waiting for updates" : `${seats} seats left`}</p>
}

export function LiveSeats({ workshopId, subscribe }) {
  return (
    <SeatUpdates
      key={workshopId}
      workshopId={workshopId}
      subscribe={subscribe}
    />
  )
}
```

Here I key the inner component by workshop ID. When I switch workshops, React gives the new counter fresh state, so it starts with “Waiting for updates.” A subscription is cleaned up when its component unmounts. Within a mounted component, React cleans up the previous setup before running the new one if a dependency changes.

```text
Render → commit UI → Effect subscribes
Dependency changes → old cleanup → new setup
Component leaves → cleanup
```

I list the reactive values the Effect reads, including props, state and functions declared in the component. An empty array fits an Effect with no reactive dependencies. Omitting the array makes the Effect run after every commit of that component. With development Strict Mode I can see an extra setup, cleanup and setup on mount. I use that sequence to check whether my cleanup really undoes my setup.

If my Effect keeps reconnecting, I check whether a dependency is a new object or function on every render. I can move configuration inside the Effect or supply a stable function where it is owned. If I need the number of visible workshops, I compute it during render. If clicking Book sends a request, I start it in the click handler. [React useEffect](https://react.dev/reference/react/useEffect)

## 3. useRef — I keep a handle between renders

```jsx
import { useRef } from "react"

export function WorkshopSearchField() {
  const inputRef = useRef(null)

  function focusSearch() {
    inputRef.current?.focus()
  }

  return (
    <div>
      <label>
        Search workshops
        <input ref={inputRef} type="search" />
      </label>
      <button type="button" onClick={focusSearch}>Focus search</button>
    </div>
  )
}
```

React fills `inputRef.current` with the DOM node when it attaches the input and clears it when the node is removed. I read the ref in the click handler. I also use refs for timer IDs or other handles I need to keep across renders. A write to `.current` does not schedule a render, so if a value should update the text on screen, I keep it in state. I normally read and write refs in handlers or Effects and keep render pure. [React useRef](https://react.dev/reference/react/useRef)

## 4. useMemo — I reuse expensive derived work

Suppose my workshop catalogue is large and searching and sorting it takes noticeable time. I measure before wrapping the calculation.

```jsx
import { useMemo } from "react"

export function WorkshopResults({ workshops, query }) {
  const search = query.trim().toLowerCase()

  const matches = useMemo(() => {
    return workshops
      .filter(({ title }) => title.toLowerCase().includes(search))
      .sort((left, right) => left.title.localeCompare(right.title))
  }, [workshops, search])

  return (
    <ul>
      {matches.map(({ id, title }) => <li key={id}>{title}</li>)}
    </ul>
  )
}
```

I sort the array returned by `filter`, so the original workshop array stays untouched. When the search or workshops references change, React recalculates the result. If the parent recreates the workshops array on every render, the new reference can defeat the cache. I keep the calculation pure and expect it to work even when React recomputes it. I skip `useMemo` for cheap work, and I look at list virtualisation separately if the slow part is rendering too many rows. [React useMemo](https://react.dev/reference/react/useMemo)

## 5. useReducer — I describe changes as actions

On the search page, changing the query or toggling the availability filter should reset pagination. I put those transitions in one reducer so each handler can say what happened.

```jsx
import { useReducer } from "react"

const initialFilters = { query: "", onlyAvailable: false, page: 1 }

export function filterReducer(state, action) {
  switch (action.type) {
    case "queryChanged":
      return { ...state, query: action.query, page: 1 }
    case "availabilityToggled":
      return { ...state, onlyAvailable: !state.onlyAvailable, page: 1 }
    case "nextPage":
      return { ...state, page: state.page + 1 }
    case "reset":
      return initialFilters
    default:
      throw new Error(`Unknown filter action: ${action.type}`)
  }
}

export function WorkshopFilters() {
  const [filters, dispatch] = useReducer(filterReducer, initialFilters)

  return (
    <div>
      <label>
        Search workshops
        <input
          value={filters.query}
          onChange={(event) => dispatch({
            type: "queryChanged",
            query: event.target.value
          })}
        />
      </label>
      <label>
        <input
          type="checkbox"
          checked={filters.onlyAvailable}
          onChange={() => dispatch({ type: "availabilityToggled" })}
        />
        Only show available workshops
      </label>
      <p>Page {filters.page}</p>
      <button type="button" onClick={() => dispatch({ type: "nextPage" })}>
        Next page
      </button>
      <button type="button" onClick={() => dispatch({ type: "reset" })}>
        Reset filters
      </button>
    </div>
  )
}
```

I can start from page 3, type a new query and expect page 1 with the new query and the old availability filter. I can check that transition by calling `filterReducer` directly. A reducer takes the current state and an action and returns the next state. I keep network calls and other side effects out of it. For an independent toggle, I usually stay with `useState`. [React useReducer](https://react.dev/reference/react/useReducer)

## 6. Context — I share a value across a subtree

I want a toolbar and several workshop cards to use the same display language. I put the preference in a provider near the root of that subtree and read it wherever I need it.

```jsx
import { createContext, useContext, useState } from "react"

const LanguageContext = createContext(null)

export function LanguageProvider({ children }) {
  const [language, setLanguage] = useState("en")

  return (
    <LanguageContext.Provider value={{ language, setLanguage }}>
      {children}
    </LanguageContext.Provider>
  )
}

export function useLanguage() {
  const value = useContext(LanguageContext)

  if (value === null) {
    throw new Error("useLanguage must be used inside LanguageProvider")
  }

  return value
}

export function LanguageSwitcher() {
  const { language, setLanguage } = useLanguage()

  return (
    <button
      type="button"
      onClick={() => setLanguage(language === "en" ? "bn" : "en")}
    >
      Language: {language}
    </button>
  )
}
```

I mount `<LanguageSwitcher />` and any translated components under `<LanguageProvider>`. Each reader gets the value from its nearest provider above it. Context distributes the preference. The `useState` in the provider still owns it.

When the provider value changes, consumers reading that context update. The object literal here creates a new value on each provider render. This is fine for a small example. In measured hot paths, I can stabilise the value or split frequently changed data from unrelated preferences so fewer readers update. [React useContext](https://react.dev/reference/react/useContext)

## 7. Custom Hooks — I reuse behavior

A workshop detail view and a chat view both need to show when the browser reports being offline. I can keep the subscription and cleanup in one Hook and let each component choose how it presents the result.

```jsx
import { useEffect, useState } from "react"

export function useOnlineStatus() {
  const [online, setOnline] = useState(null)

  useEffect(() => {
    function syncStatus() {
      setOnline(navigator.onLine)
    }

    window.addEventListener("online", syncStatus)
    window.addEventListener("offline", syncStatus)
    syncStatus()

    return () => {
      window.removeEventListener("online", syncStatus)
      window.removeEventListener("offline", syncStatus)
    }
  }, [])

  return online
}

export function NetworkNotice() {
  const online = useOnlineStatus()
  return online === false ? <p role="status">You appear to be offline</p> : null
}
```

I start with an unknown status so the first render can also happen on the server. The client Effect reads the browser status and keeps it up to date. This status tells me what the browser reports about the connection. I still handle a failed API call separately.

Each call to a custom Hook gets its own state and Effect. If I need every component to read one shared state instance, I put the Hook in a common parent or a Context provider and share its result. If I am extracting a plain filter function that calls no Hooks, I keep it a normal function. [React custom Hooks](https://react.dev/learn/reusing-logic-with-custom-hooks)

## A quick revision pass

I cover the answers in the right column and try to explain them aloud.

| Question | What I expect |
| --- | --- |
| Why did two `setQuantity(quantity + 1)` calls add only one? | Both calls saw the same render's quantity. Functional updaters build on the queued value. |
| Why did the subscription open twice during development? | Strict Mode can run an extra setup and cleanup cycle. One live subscription should remain after setup. |
| Why did changing `ref.current` leave the UI unchanged? | A ref write does not schedule a render. I use state for values shown on screen. |
| Why does my memo run again? | One input may have a different identity, such as an array rebuilt on each render. |
| When do I reach for a reducer? | Several actions change related fields and I want to see and test the transitions in one place. |
| Do two components share state just because both call the same Hook? | Each call owns its own state unless the Hook reads from a shared owner such as a provider. |
