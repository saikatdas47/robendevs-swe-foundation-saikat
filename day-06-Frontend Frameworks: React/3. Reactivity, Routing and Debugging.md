# Day 06 — Reactivity, Routing and Debugging

I continue with my workshop app. I follow three actions I can reproduce while revising. I change one workshop's seat count, open its detail page and investigate why its card renders again.

## 1. How frameworks update the UI

I start with the same change everywhere. Workshop 42 has three seats and a booking reduces it to two.

| Framework | What I change | How that reaches the screen |
| --- | --- | --- |
| React | I call a state setter with an updated value. | React renders the affected component tree, reconciles the new element output with the previous tree and commits the necessary DOM changes. |
| Vue | I update a reactive value, such as `seats.value` for a ref in script. | Vue tracks reactive reads during rendering. A change schedules an update for the affected component. Vue compares virtual nodes and uses compiler hints to focus on dynamic parts of the template. |
| Angular | I update a signal, such as `seats.set(2)`. | Angular tracks the signal read by the template and marks the relevant view for a check. Change detection evaluates template bindings and updates the DOM where a binding value changed. |
| Svelte | I update reactive state, such as a variable declared with `$state`. | The compiler generates update code for reactive parts of the component. At runtime, changing the state causes the dependent output to update. |

In React I separate **rendering** from **committing**. Rendering runs component functions to work out the next UI. Committing applies the result. If I change a seat count from three to two, a component can run again while the browser only needs one text update.

```text
Seat state changes
       ↓
React renders the card and reconciles its output
       ↓
Commit updates the seat count text
```

I use stable keys to describe identity among siblings. If I filter the list and then reorder it, `key={workshop.id}` helps React match each card with the right workshop. An array index can make local card state follow the position when rows move.

In Angular, signals and change detection work together. A signal read in an `OnPush` template tells Angular which view depends on it. Angular can skip eligible subtrees during checks. In Svelte, compilation happens at build time and the updates happen in the browser when state changes. [React render and commit](https://react.dev/learn/render-and-commit) · [Vue rendering mechanism](https://vuejs.org/guide/extras/rendering-mechanism.html) · [Angular signals](https://angular.dev/guide/signals) · [Svelte state](https://svelte.dev/docs/svelte/$state)

## 2. Routing and server data caching

I map `/workshops` to the list and `/workshops/42` to the detail view. The router matches the URL, extracts the ID and decides which layout and page to render. I use the URL for a filter such as `?topic=css` when the filtered view needs to survive refresh or be shareable. I still test a direct visit, Back, Forward and an unknown workshop ID.

| App | Where I define routes and start loading |
| --- | --- |
| React app with React Router | I configure a route such as `workshops/:id`. In a data router I can fetch in a route loader and render its result in the route. |
| Vue app with Vue Router | I configure a route record and read its params. I can fetch in the view or during navigation, depending on when I want to show loading feedback. |
| Angular app | I use Angular Router route records. A resolver can load essential data before route activation. |
| SvelteKit app | I define a file route such as `src/routes/workshops/[id]/+page.svelte` and use a route `load` function. |

I treat loading and cache reuse separately. A route loader decides when data is needed. A cache decides whether an existing result is still suitable for reuse.

1. I open workshop 42. The client looks up a key such as `["workshop", "42"]` and fetches the detail if needed.
2. I go Back, then open 42 again. If the cached detail is fresh, I can reuse it. If it is stale, I can show it while refreshing in the background when the screen allows that.
3. I book a seat. I update the cached count from the response or invalidate the detail and affected lists. The booking API checks current stock regardless of what the UI cached.

I keep track of where the cached value lives. A client query cache helps with navigation in a running app. An HTTP cache follows response headers. A server framework cache may reuse a fetch result or rendered HTML across requests. I include relevant filters in client keys and avoid sharing personalised responses across users. [React Router data loading](https://reactrouter.com/start/data/data-loading) · [Vue Router data fetching](https://router.vuejs.org/guide/advanced/data-fetching.html) · [Angular resolvers](https://angular.dev/guide/routing/data-resolvers) · [SvelteKit loading data](https://svelte.dev/docs/kit/load)

## 3. What the application frameworks add

My public workshop detail page needs a shareable URL and useful initial HTML. My staff dashboard needs session checks and fresh data. These tools bring routing, server execution and rendering conventions together, so I decide those behaviors at the route level.

| Tool | What it adds to the UI framework | Workshop example |
| --- | --- | --- |
| Next.js for React | File-based App Router, layouts, server rendering, Server Components and Route Handlers | I fetch public workshop details on the server and use a Client Component for the interactive booking button. |
| Nuxt for Vue | File-based routing, server rendering and route rules, server endpoints and data-loading helpers | I use `useAsyncData` to load a detail page and let Nuxt pass the server result to the browser during hydration. |
| Angular SSR | Server rendering, prerendering and hydration integrated with Angular and its router | I prerender a public guide and use request-time rendering for routes that need it. |
| SvelteKit for Svelte | File-based routing, layouts, server load functions, form actions and per-route rendering options | I load public workshop data in a route and handle a booking form with a server action. |

For a public description I can use a server cache or prerender the page if changes are infrequent. I keep private booking details and live availability on a separate freshness policy. SSR describes where HTML is produced. Hydration connects client behavior to that HTML. The framework's data-loading and cache settings determine which work can be reused. ## 4. How I debug re-renders

I reproduce one action at a time. If typing in Search feels slow, I record one keystroke with the React DevTools Profiler. I look at which components committed, how long they took and whether the delay is rendering work, a network wait or something else. Then I make a small change and record the same action again.

| What I observe | What I check |
| --- | --- |
| Typing renders an expensive section that never reads the query | I check whether I lifted state too high. I can move it closer to the input and the results that depend on it. |
| A memoised card still renders after an unrelated update | I check whether the parent creates new object or function props on each render. I can pass the specific primitive values the card needs. The card can still render when its own state or consumed context changes. |
| The wrong card stays expanded after filtering | I check whether I used list positions as keys and switch to stable workshop IDs. |
| An Effect reconnects after each render | I check which dependency keeps changing and whether the Effect needs that dependency as currently structured. In development Strict Mode, I also check whether I am seeing its extra setup and cleanup cycle. |
| Many context readers update together | I check what changed in the provider value and whether unrelated data belongs in different contexts. |

For example, if a memoised `WorkshopCard` receives `display={{ title, seats }}`, the object is new whenever the parent renders. I can pass `title={title}` and `seats={seats}` so unchanged values compare equal. I profile again to see whether skipping the card's work actually improves the interaction.

In Vue DevTools I inspect the component tree and reactive state. In Angular DevTools I use the profiler to see change detection activity and which components take time. In Svelte I can use the development-only `$inspect` rune for a reactive value and the browser's Performance panel for slow interactions. I also use Network to check whether navigating twice sends an unexpected second API request. [React Profiler](https://react.dev/reference/react/Profiler) · [Vue DevTools](https://devtools.vuejs.org/) · [Angular DevTools](https://angular.dev/tools/devtools) · [Svelte inspect](https://svelte.dev/docs/svelte/$inspect)
