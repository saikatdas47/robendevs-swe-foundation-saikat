# Day 06 — React Internals, Performance and Migration

I use the workshop app to follow what React does when I type a filter, open a report and load a page from the server. Then I use the same app to think through an AngularJS migration and a framework choice.

## 1. Reconciliation and Fiber

When I filter the workshop list, React runs the components involved to calculate the next UI. During **reconciliation**, it matches the new element tree with the previous one. During the **commit**, it applies the changes that made it into the finished render. A component function can run again even when React ends up leaving its DOM alone.

I think about identity when the list changes from `[A, B, C]` to `[C, A]`. With `key={workshop.id}`, React can match C to the previous C and preserve its local state. B is removed and loses its local state. If I key by position, the first row can keep A's state while displaying C's data. Keys describe identity among siblings, along with element type. I can deliberately change a key to reset something like a signup form when the workshop changes.

**Fiber** is React's internal representation of the tree and its units of work. I picture React calculating a work-in-progress tree while the current committed UI stays visible. React can pause, resume or discard interruptible render work when a more urgent update arrives. Once it commits a completed update, the DOM changes are applied synchronously. This is why I keep component rendering pure. A render can run without ever being committed.

```text
State update → React prepares work on the tree
                    │
                    ├─ urgent work arrives → interruptible render can restart
                    │
                    └─ completed render → commit changes to the DOM
```

## 2. Transitions and Suspense

### I keep typing responsive while results catch up

I need the input text to update immediately. Rendering a large results panel can wait briefly, so I mark the results update as a transition.

```jsx
import { memo, useState, useTransition } from "react"

const Results = memo(function Results({ workshops, query }) {
  const search = query.trim().toLowerCase()
  const matches = workshops.filter(({ title }) =>
    title.toLowerCase().includes(search)
  )

  return <ul>{matches.map(({ id, title }) => <li key={id}>{title}</li>)}</ul>
})

export function WorkshopSearch({ workshops }) {
  const [input, setInput] = useState("")
  const [query, setQuery] = useState("")
  const [isPending, startTransition] = useTransition()

  function handleChange(event) {
    const value = event.target.value
    setInput(value)
    startTransition(() => setQuery(value))
  }

  return (
    <section>
      <label>
        Search workshops
        <input value={input} onChange={handleChange} />
      </label>
      <p role="status">{isPending ? "Updating results…" : ""}</p>
      <Results workshops={workshops} query={query} />
    </section>
  )
}
```

With a stable `workshops` reference, the memoised list can skip the urgent render while its query stays the same. If I type again while React works on the results, the input update can interrupt the results render. I keep the controlled input update outside the transition. A transition does not debounce requests or move work to another thread. A long synchronous filter still occupies the thread until that calculation returns. If the filter itself is slow, I measure it and consider indexing or moving the computation off the main thread. [React useTransition](https://react.dev/reference/react/useTransition)

### I decide what remains visible while a section loads

I put a Suspense boundary around a report that I load only when the user opens it. The page header and controls stay outside the boundary.

```jsx
import { lazy, Suspense, useState } from "react"

const Report = lazy(() => import("./Report.jsx"))

export function WorkshopReports() {
  const [open, setOpen] = useState(false)

  return (
    <section>
      <h2>Workshop reports</h2>
      <button type="button" onClick={() => setOpen(true)}>Open report</button>
      {open && (
        <Suspense fallback={<p role="status">Loading report…</p>}>
          <Report />
        </Suspense>
      )}
    </section>
  )
}
```

I give `Report.jsx` a default component export. On the first open, the boundary can show the fallback until the chunk is ready. A framework can also integrate Suspense with server data and streaming. A fetch I start inside `useEffect` still needs its own loading state. If the import rejects, I handle it with an Error Boundary. If a transition suspends an already visible section, React can keep the previous content visible while the replacement gets ready. [React Suspense](https://react.dev/reference/react/Suspense) · [React lazy](https://react.dev/reference/react/lazy)

## 3. Server Components and hydration

On my public workshop page, I can read the title and description in a Server Component using a framework that supports React Server Components. The framework sends the rendered result, and the browser does not need the Server Component's implementation in its client bundle. I put the interactive Book button in a Client Component so it can use state and click handlers. I pass it the workshop ID and let the server validate any booking request.

```text
Server Component reads the public workshop
├── Title and description come from its rendered output
└── Client Component receives the workshop ID
    └── Booking button can handle clicks after hydration
```

I separate the component boundary from SSR. **SSR** produces initial HTML on the server. **Server Components** determine which component code runs only on the server and what output crosses to the client. A framework can use both on the same initial request. Client Components can also contribute to the initial HTML in that setup, then hydrate in the browser. I keep server credentials in server-only code and avoid passing private data across the client boundary. [React Server Components](https://react.dev/reference/rsc/server-components) · [React use client](https://react.dev/reference/rsc/use-client)

## 4. Performance across frameworks

I start with one slow interaction and measure a comparable production build. I use the same route, data, images, device profile and cache conditions when comparing implementations. I check compressed JavaScript transfer, main-thread work and when the important controls become usable. I also test a repeat navigation because cached chunks can change what dominates the wait.

| What I investigate | What I compare |
| --- | --- |
| Memoisation | In React, I use `memo` for an expensive child that receives the same props often, or `useMemo` for a measured calculation. I pay for comparisons, retain cached values and may complicate the code. New object props can defeat the benefit. Vue computed values cache derived work based on reactive dependencies. Angular computed signals and Svelte derived state also track what the calculation reads. |
| Bundle size | I look at the route's client JavaScript, runtime and third-party packages. React and Vue ship runtime code. Angular can split routes and defer selected views. Svelte compiles component updates but still ships generated JavaScript and any needed runtime helpers. In every app, a large shared dependency can dominate the result. |
| Hydration cost | When I serve HTML first, the browser may still need to download, parse and execute code before the UI handles input. I measure that work as well as the HTML arrival time. A React app can ship less client code with Server Components. In Nuxt, Angular SSR or SvelteKit I inspect which sections actually need client interaction and which rendering or hydration features my setup supports. |

For example, if the workshop page ships a chart library just to show a report most visitors never open, I split that feature before adding memoisation to every card. If typing still feels slow, I profile the keystroke and inspect the components that render. SSR can make the title readable early while the booking button is still waiting for client code. I measure both experiences. [React memo](https://react.dev/reference/react/memo) · [Vue performance](https://vuejs.org/guide/best-practices/performance.html) · [Angular incremental hydration](https://angular.dev/guide/incremental-hydration) · [SvelteKit page options](https://svelte.dev/docs/kit/page-options)

## 5. How I migrate AngularJS a piece at a time

I imagine the old workshop portal has public schedules, bookings and an admin area. I first map routes, shared services and session behavior. I write a few end-to-end checks for login and booking so I can compare the old and new implementations while both are running.

1. I pick a bounded route with a clear API, such as the public schedule. I keep the booking API contract and session rules stable during the move.
2. I choose the integration boundary. For Angular, I can use `@angular/upgrade/static` to run a hybrid app and bridge components and services. For another framework, I can route an entire URL to the new app or mount it in a dedicated container. I let one framework own each DOM subtree.
3. I route a small share of traffic to the new screen or put it behind a feature flag. I compare login behavior, deep links, Back navigation, error rates and page performance. I keep a way to return the route to the old screen.
4. I migrate neighbouring screens once the first one holds up. After moving the last caller of an old service or bridge, I remove it and check that the route still works without AngularJS.

I account for the overlap. Two frameworks can mean two runtimes, duplicated tooling and more difficult debugging. AngularJS official support ended in January 2022, so I track which routes still depend on it and use that inventory to finish the migration. [Angular UpgradeModule](https://angular.dev/api/upgrade/static/UpgradeModule) · [AngularJS support status](https://docs.angularjs.org/misc/version-support-status)

## 6. How I choose a framework

| What I ask | What I look for |
| --- | --- |
| Team skills | I check whether the team can debug, test and review the app confidently. I include onboarding and training time. |
| Ecosystem | I try the routing, forms, data fetching and accessibility tools my project needs. I check who maintains important dependencies and how awkward they are to replace. |
| Hiring | I look at the hiring pool I can actually reach and how quickly developers with related experience can become productive. |
| Long-term support | I check the official support policy, upgrade process and release cadence. I budget for updating the framework and the surrounding libraries. |
| Project type | I decide whether my main problem is public content, interactive dashboards, complex forms or incremental migration. I validate the choice with one realistic route. |

For a form-heavy internal portal, I might prefer Angular if my team values its built-in forms, dependency injection and conventions. If a React team needs public workshop pages plus interactive booking, I would prototype one route in Next.js. A Vue team can test the same flow in Nuxt, and a Svelte team can test it in SvelteKit. For a long-lived AngularJS app, I give migration boundaries and the ability to ship small changes as much weight as the new app's component syntax. [Angular release and support policy](https://angular.dev/reference/releases)
