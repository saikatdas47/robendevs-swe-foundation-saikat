# Backend Fundamentals

## 1. Request Handling

On Day 1 I followed a request across the network. Here I pick it up at the backend. I use JavaScript on Node.js v26 with Express 5 so I can follow the request from the TCP socket to my route handler.

### From a listening socket to my handler

When I call `app.listen(3000, "127.0.0.1")`, the runtime asks the operating system to bind a TCP socket to that address and port and listen for connections. When a client connects, the listening socket stays available and the server gets a connected socket for that client. The connected socket carries bytes in both directions.

Express starts a Node.js HTTP server for my app. The HTTP server parses those bytes into a request method, target and headers. It can give my handler access to the body as a stream while more bytes arrive. With HTTP/1.1 keep-alive, I can receive several requests over the same TCP connection. I route each request separately.

```text
Client
  │ TCP connection
  ▼
Connected socket
  │ bytes
  ▼
HTTP server
  │ method, path, headers and body stream
  ▼
Express router
  │ picks a handler by method and path
  ▼
Handler
  │ writes status, headers and body
  ▼
HTTP server → socket → client
```

### I route a request with Express

I run `npm init -y` and `npm install express@5` in my practice folder. I save this as `server.mjs` and start it with `node server.mjs`.

```javascript
import express from "express"

const app = express()

app.get("/health", (req, res) => {
  res.json({ status: "ok" })
})

app.all("/health", (req, res) => {
  res.set("Allow", "GET, HEAD")
  res.status(405).json({ error: "Method not allowed" })
})

app.use((req, res) => {
  res.status(404).json({ error: "Route not found" })
})

app.listen(3000, "127.0.0.1")
```

```sh
curl -i 'http://127.0.0.1:3000/health?check=1'
curl -i -X POST http://127.0.0.1:3000/health
curl -i http://127.0.0.1:3000/missing
```

I get `200` for the health check. Express matches the path without the query string and also handles `HEAD` through my GET route. I register the `405` handler after that route so it catches other methods on the same path. My final middleware sends `404` when no route responds. For a route that accepts JSON, I can use `express.json({ limit: "16kb" })` and validate `req.body`.

[Express routing](https://expressjs.com/en/guide/routing/) · [Node.js v26 HTTP API](https://nodejs.org/docs/latest-v26.x/api/http.html)

## 2. Processes and Threads

When I run `node server.mjs`, the operating system starts a process. That process has an ID, its own virtual address space and resources such as open files and sockets. If I start another copy, it gets its own process ID and address space. I can pass data between the two through a socket or another form of interprocess communication.

A thread is a flow of execution inside a process. Each thread has its own stack and CPU execution state. Threads in a process share its address space, so shared data may need coordination when multiple threads can read and write it.

### What the scheduler does

I think about a thread in three basic states.

```text
Ready ── scheduler assigns CPU time ──► Running
Ready ◄── preempted or yields ────────── Running
                                          │
                                      waits for I/O
                                          ▼
Ready ◄── I/O can continue ─────────── Waiting
```

A ready thread can run as soon as the operating system schedules it. A waiting thread can become ready when the event it depends on occurs. It still has to get CPU time. When the OS switches between threads, it saves the outgoing thread's execution state and restores the incoming thread's state.

On one logical CPU, the scheduler can interleave work from several threads. With multiple logical CPUs, threads can also execute at the same time. I call those ideas concurrency and parallelism, respectively.

### Where my JavaScript runs

In a basic Node server, my request handlers run on the main JavaScript thread. The process can have other threads doing runtime work, including libuv workers. The operating system schedules those threads. The Node event loop decides when my ready callbacks get a turn on the main thread.

If I add an expensive calculation directly to a handler, the main thread stays busy until the calculation returns. During that time, it cannot start another handler. I can move CPU-heavy JavaScript to a worker using `node:worker_threads`. A worker runs JavaScript in its own execution environment and can communicate with the main thread through messages. I can also run multiple server processes when I want separate process memory and failure boundaries.

[Node.js v26 worker threads](https://nodejs.org/docs/latest-v26.x/api/worker_threads.html) · [Linux scheduling manual](https://man7.org/linux/man-pages/man7/sched.7.html)

## 3. Blocking and Non-blocking I/O

When my backend reads a file, receives bytes from a socket or waits for a database reply, it is doing I/O. I ask what the calling thread can do while the operation is pending.

| Approach | What I see in a request handler |
| --- | --- |
| Blocking | The call keeps the thread occupied until the operation returns |
| Non-blocking | The thread can handle other ready work and return to this request when it can make progress |

At the OS level, a non-blocking socket read can return immediately when there are no bytes ready. The event loop can wait for socket readiness before trying again. At the application level, I often work with an async API that reports the result later. In Node, network I/O usually uses the OS readiness or completion mechanisms. Async file APIs such as `readFile` from `node:fs/promises` use the libuv thread pool. A pool thread can do file work while my main JavaScript thread remains available.

### I compare two file reads

I save this as `io.mjs` and run `node io.mjs`. I use the script itself as the input file.

```javascript
import { readFileSync } from "node:fs"
import { readFile } from "node:fs/promises"

const file = new URL(import.meta.url)

console.log("start sync read")
readFileSync(file)
console.log("sync read finished")

const pendingRead = readFile(file)
console.log("async read requested")
await pendingRead
console.log("async read finished")
```

I can only reach `sync read finished` after the synchronous call returns. With the promise-based read, I reach `async read requested` before I wait for the result. In an async handler, `await` suspends that handler and lets the thread continue once the current JavaScript stack has cleared. I can still block the thread with a long loop inside an async function because the loop itself runs synchronously.

[Node.js v26 file system API](https://nodejs.org/docs/latest-v26.x/api/fs.html) · [Node.js event loop and worker pool](https://nodejs.org/en/learn/asynchronous-work/dont-block-the-event-loop)

## 4. Configuration and Local Secrets

I read configuration at startup because I want the same server code to run locally and in deployment. I can keep shared defaults in a versioned config file, use environment variables for deployment-specific values and keep local credentials in a private `.env` file. I validate the final values before I start listening.

| Source | What I put there |
| --- | --- |
| `config.json` | Shared defaults such as a port or log level |
| Environment variables | Settings supplied when the process starts, such as `PORT` |
| Local `.env` | Local values such as a development database credential |
| Committed `.env.example` | Variable names and safe example values for setup |

### I load and validate a port

I save `{"port":3000}` in `config.json` and use this as `config.mjs`.

```javascript
import { readFileSync } from "node:fs"

const defaults = JSON.parse(
  readFileSync(new URL("./config.json", import.meta.url), "utf8")
)

const port = Number(process.env.PORT ?? defaults.port)

if (!Number.isInteger(port) || port < 1 || port > 65535) {
  throw new Error("PORT must be an integer from 1 to 65535")
}

console.log({ port })
```

I can run `node config.mjs` to get `3000`. If I put `PORT=4000` in `.env` and run `node --env-file=.env config.mjs`, I get `4000`. If I run `PORT=5000 node --env-file=.env config.mjs`, the already-set environment variable wins and I get `5000`. Values I read from `process.env` are strings, so I convert and check the value before using it.

I add `.env` to `.gitignore` and commit `.env.example` with placeholders. I keep actual secrets out of logs and shared configuration. In a deployed service, I let the deployment platform supply secrets at runtime.

[Node.js v26 environment variables](https://nodejs.org/docs/latest-v26.x/api/environment_variables.html) · [Node.js v26 command-line API](https://nodejs.org/docs/latest-v26.x/api/cli.html#--env-filefile)

## 5. Dependencies and Semantic Versioning

When I install a package, it can bring in packages of its own. The package I declare is my direct dependency. The packages it needs are transitive dependencies. Together they form a dependency tree.

In a Node project I see three parts.

| Part | How I use it |
| --- | --- |
| `package.json` | I declare the packages the project needs and the versions or ranges it accepts |
| `package-lock.json` | I keep npm's resolved dependency tree, including exact versions and integrity information where available |
| `node_modules/` | I use the installed packages locally and recreate this directory from the project files |

I ran `npm install express@5` to add Express 5 as a direct dependency and commit the manifest and lock file together. In CI I run `npm ci` for a clean installation from the lock file. If the manifest and lock file disagree, `npm ci` fails so I can fix them together.

### I read a version range

I read `2.4.3` as major 2, minor 4 and patch 3. For a stable public API, SemVer uses a patch increment for compatible bug fixes, a minor increment for compatible features and a major increment for breaking changes.

| Version I write | What it accepts in this example |
| --- | --- |
| `2.4.3` | Exactly 2.4.3 |
| `~2.4.3` | From 2.4.3 up to but excluding 2.5.0 |
| `^2.4.3` | From 2.4.3 up to but excluding 3.0.0 |
| `^0.4.3` | From 0.4.3 up to but excluding 0.5.0 |

I compare ordinary releases in this table. The caret follows stricter bounds for early versions such as `0.4.3`. If my manifest says `^2.4.3` and my lock file records `2.4.7`, a clean install uses `2.4.7`. The manifest describes what I allow and the lock file records what npm selected.

[Semantic Versioning specification](https://semver.org/) · [npm install](https://docs.npmjs.com/cli/install/) · [npm ci](https://docs.npmjs.com/cli/commands/npm-ci/)

## 6. Errors and Logs

When a request fails, I decide what the caller needs and what I need to investigate. If an ID has an invalid format, I can send a clear `400`. If the ID is valid and the record is absent, I can send `404`. If an unexpected dependency failure prevents the request from finishing, I can send a generic `500` and record details in the server log.

### I handle route errors in middleware

I save this as `errors.mjs` in the same practice folder and run `node errors.mjs`. I use a small lookup with one record and a simulated failure so I can try each response without setting up a database.

```javascript
import express from "express"
import { randomUUID } from "node:crypto"

const app = express()

app.use((req, res, next) => {
  const requestId = randomUUID()
  const startedAt = performance.now()
  res.locals.requestId = requestId
  res.set("X-Request-Id", requestId)

  res.on("finish", () => {
    console.info(JSON.stringify({
      level: "info",
      timestamp: new Date().toISOString(),
      requestId,
      event: "response_finished",
      status: res.statusCode,
      durationMs: Math.round(performance.now() - startedAt)
    }))
  })

  next()
})

async function findUser(id) {
  if (id === "999") {
    throw new Error("User lookup failed")
  }

  return id === "1" ? { id, name: "Riya" } : null
}

app.get("/users/:id", async (req, res) => {
  const { id } = req.params

  if (!/^\d+$/.test(id)) {
    return res.status(400).json({ error: "User ID must contain only digits" })
  }

  const user = await findUser(id)

  if (user === null) {
    return res.status(404).json({ error: "User not found" })
  }

  res.json(user)
})

app.use((error, req, res, next) => {
  console.error(JSON.stringify({
    level: "error",
    timestamp: new Date().toISOString(),
    requestId: res.locals.requestId,
    event: "request_failed",
    errorType: error instanceof Error ? error.name : "UnknownError"
  }))

  if (res.headersSent) {
    return next(error)
  }

  res.status(500).json({ error: "Internal server error" })
})

app.listen(3001, "127.0.0.1")
```

```sh
curl -i http://127.0.0.1:3001/users/1
curl -i http://127.0.0.1:3001/users/abc
curl -i http://127.0.0.1:3001/users/2
curl -i http://127.0.0.1:3001/users/999
```

I get `200`, `400`, `404` and `500` in that order. Express 5 forwards a rejected async handler to my four-argument error middleware. When headers have already gone out, I call `next(error)` to let Express handle the partial response.

I match the error entry and response entry using the request ID. The `finish` event marks when Node hands the response off to the operating system. I keep credentials, authorization headers and raw request bodies out of these logs.

[Express error handling](https://expressjs.com/en/guide/error-handling/) · [Node.js v26 HTTP response API](https://nodejs.org/docs/latest-v26.x/api/http.html#class-httpserverresponse)
