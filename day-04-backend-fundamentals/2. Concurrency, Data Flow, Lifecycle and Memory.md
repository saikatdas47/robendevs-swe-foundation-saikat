# Concurrency, Data Flow, Lifecycle and Memory

In the first note I followed a request from the socket to my Express handler. Here I look at what happens when requests overlap, when a client reads slowly and when I need to stop the server while work is still running. I use Node.js v26 and Express 5 for the examples.

## 1. Concurrency models

I picture two requests arriving together. Request A is waiting for a database reply and request B can already do useful work. The concurrency model determines where each request waits and what can run in the meantime.

| Model | How I follow the two requests |
| --- | --- |
| Thread per request | A and B each get an OS thread for the duration of the request. If A blocks on I/O, B can still run. Many waiting requests can still occupy many threads and their stacks. |
| Thread pool | I reuse a fixed group of threads. A job waits in a queue when all workers are busy. If a worker blocks inside a job, another job needs a free worker. |
| Event loop | I run ready handlers on an event-loop thread. While A waits for an async operation, the loop can run B. A long calculation on the loop delays both requests. |
| Async and await | I write A as a sequence of steps. When A awaits a pending promise, it suspends and resumes later. The operation behind that promise determines how the actual work runs. |
| Lightweight threads | A runtime schedules many execution units, such as goroutines or virtual threads, over fewer OS threads. Many waits can suspend a lightweight thread while its underlying OS thread runs other work. The details depend on the runtime. |

In my Express app, JavaScript route handlers run on the main event-loop thread by default. Node uses its libuv pool for some operations such as async file reads. If I need to run CPU-heavy JavaScript in parallel, I can use JavaScript worker threads. Those workers are separate from the pool that handles file reads.

```text
A starts → A awaits a pending I/O result → B runs → A resumes when ready
```

[Node.js event loop and worker pool](https://nodejs.org/en/learn/asynchronous-work/dont-block-the-event-loop)

## 2. Shared state

I get a race condition when my result depends on which operation runs first. It can happen in Express even on one JavaScript thread because an `await` lets another request run before the first request resumes.

I save this as `race.mjs` and run `node race.mjs`. Both calls read the same value before either writes it back.

```javascript
let count = 0

async function increment() {
  const previous = count
  await Promise.resolve()
  count = previous + 1
}

await Promise.all([increment(), increment()])
console.log(count)
```

I get `1` after two increments. Both calls read `0` and both write `1`. For this in-memory counter on one event-loop thread, I can keep the update together as `count += 1` with no await in the middle. For a counter shared by several server processes, I can use an atomic increment in the database.

When several threads can change the same state, I can use a mutex to allow one thread at a time into the section that reads and updates it. I release the mutex even if that work fails, usually with a `finally` block. I call the operation thread-safe when concurrent calls preserve the guarantees I expect, such as counting every increment exactly once. Keeping shared data immutable or letting one thread own it can also help.

I can create a deadlock if one worker holds lock A and waits for lock B while another holds B and waits for A. Both workers need the other to release a lock before they can continue. If both workers always acquire A before B, they avoid this particular cycle.

## 3. Streams, buffering and backpressure

When I send a large file, I can read and write it in chunks. A buffer holds chunks temporarily while the next part of the system catches up. If the client reads slower than I can read the file, bytes start collecting on the write side.

Backpressure is how the write side tells the read side to slow down. In Node, a writable stream returning `false` from `write()` asks me to wait for `drain` before writing more. That chunk was accepted into the writable stream. I let `pipeline()` coordinate the flow and clean up the streams if the transfer fails.

```text
File → readable stream → write buffer → socket → client
               ▲              │
               └── slow down ─┘
```

I add this route to my Express app before the fallback middleware. I put `notes.txt` next to my server file and request `GET /download`.

```javascript
import { open } from "node:fs/promises"
import { pipeline } from "node:stream/promises"

const notesFile = new URL("./notes.txt", import.meta.url)

app.get("/download", async (req, res) => {
  const file = await open(notesFile)

  res.type("text/plain")
  await pipeline(file.createReadStream(), res)
})
```

I open the file before streaming so a failed open can reach my Express error middleware before I start writing. If the transfer fails after it starts, the pipeline can close the response. I use a fixed file path so the request does not choose a file on disk.

[Node.js v26 streams](https://nodejs.org/download/release/v26.13.1/docs/api/stream.html)

## 4. Graceful shutdown and health checks

When I deploy a new version, the process manager can send my old process `SIGTERM`. In my terminal, Ctrl+C usually sends `SIGINT`. I stop accepting new work and let requests that already entered their handlers finish. I keep the resources those requests need open until they finish or my shutdown deadline expires.

| Check | What I use it for |
| --- | --- |
| Liveness | I check whether the instance can respond. A process manager can use repeated failures to decide whether to restart it. |
| Readiness | I check whether the instance should receive traffic. During shutdown, the readiness handler returns `503` if a probe can still reach it. Once the listener closes, a failed connection also makes the instance unavailable. |

I save this as `shutdown.mjs` in the practice folder where I installed Express 5. I run `node shutdown.mjs`, request `http://127.0.0.1:3002/work` and press Ctrl+C in the server terminal while that request is waiting.

```javascript
import express from "express"
import { setTimeout as delay } from "node:timers/promises"

const app = express()
let draining = false

app.get("/live", (req, res) => {
  res.sendStatus(200)
})

app.get("/ready", (req, res) => {
  res.sendStatus(draining ? 503 : 200)
})

app.use((req, res, next) => {
  if (draining) {
    return res.sendStatus(503)
  }

  next()
})

app.get("/work", async (req, res) => {
  await delay(2000)
  res.json({ status: "done" })
})

const server = app.listen(3002, "127.0.0.1")

function shutdown() {
  if (draining) return
  draining = true

  const deadline = setTimeout(() => {
    process.exitCode = 1
    server.closeAllConnections()
  }, 8000)

  server.close((error) => {
    clearTimeout(deadline)

    if (error) {
      console.error(error)
      process.exitCode = 1
    }
  })
}

process.on("SIGTERM", shutdown)
process.on("SIGINT", shutdown)
```

I use `server.close()` to stop listening and wait for active HTTP requests. The middleware also rejects new work on an existing connection if a request reaches Express while draining. At eight seconds I close remaining HTTP connections. In this example there are no database connections to clean up. In an app with a database pool, I close it after the drain and give the entire shutdown a deadline. Closing an HTTP socket by itself does not cancel database work.

[Express health checks and graceful shutdown](https://expressjs.com/en/advanced/healthcheck-graceful-shutdown/) · [Node.js v26 HTTP server](https://nodejs.org/download/release/v26.13.1/docs/api/http.html)

## 5. Stack, heap and garbage collection

I use the call stack to follow active function calls. A call pushes a frame and returning removes it. Each thread has its own stack. If I recurse without a stopping point, I can run out of stack space.

I use the heap to think about objects such as arrays, request data and caches that may outlive the call that created them. A variable in a function can refer to a heap object. The engine decides the actual memory layout.

```text
During the request

Route handler frame → user object ← cache entry

After the handler returns

                      user object ← cache entry
```

The garbage collector can reclaim objects once they are unreachable from roots such as active execution state and global references. I do not control exactly when collection runs. In the diagram, the cache still holds the user object after the handler returns, so it stays reachable.

If I keep adding objects to a long-lived cache and never remove them, memory can keep growing even though garbage collection runs. I can bound that cache or expire entries. When I inspect Node memory with `process.memoryUsage()`, I look at `heapUsed` for V8 heap usage and remember that buffers and other native allocations can also contribute to process memory.
