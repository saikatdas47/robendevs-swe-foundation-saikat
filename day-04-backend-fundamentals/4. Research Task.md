# How I Follow 1,000 Concurrent Requests

I picture a server with four available CPU cores. It has accepted 1,000 requests that are still in progress. Of those, 999 start an I/O operation, such as a database query, and one needs 200 ms of CPU time. I assume the connections and downstream service have enough capacity so I can focus on how the server schedules the work.

## Thread per request

I give each request its own operating system thread. If all 1,000 requests have started, I have 1,000 request threads. When a thread blocks waiting for I/O, it keeps its stack and request state. The operating system can leave it asleep and give CPU time to other runnable threads. When the I/O result arrives, the waiting thread becomes runnable again.

The heavy request uses CPU time on its own thread. Other runnable threads can run on the other cores. The operating system can also preempt the heavy thread and let another thread use its core. I still expect contention if many threads wake up together. They share four cores, and keeping 1,000 threads also costs memory for their stacks and bookkeeping.

## Event loop

I picture a single event-loop thread with asynchronous I/O. Each of the 999 handlers starts its I/O operation and suspends. The server keeps each request's state while it waits. When an I/O result is ready, the handler's continuation gets a turn on the loop.

If the heavy request runs its entire calculation on the event-loop thread, it occupies that thread until it gives control back. During that time, I/O can finish elsewhere, but its handlers cannot resume on the loop. A quick request that becomes ready just after the calculation begins can wait almost the full 200 ms if the calculation runs uninterrupted. It can wait longer if more work is queued by the time the loop becomes free.

```text
Time flows left to right →

Thread per request
Heavy thread   [---------- CPU work ----------]
Other threads  [I/O wait] [resume when scheduled]

Single event loop
Loop           [---------- CPU work ----------][resume ready handlers]
I/O elsewhere             [result ready] ──────►
```

## What I take from the comparison

In both models I can have 1,000 requests in progress, with many waiting for I/O. The difference I look at is where the wait happens and who can run when a result arrives. In the thread-per-request model, the OS schedules runnable request threads independently. On a single event loop, every ready handler on that loop waits behind a long synchronous calculation.

I can move the heavy calculation to a bounded worker pool so the event loop can keep serving ready requests while the worker runs. The calculation still needs CPU time, and the pool can queue work when its workers are busy. If the server runs multiple event loops, a synchronous calculation directly stalls the loop running it, while CPU contention can still affect the others.
