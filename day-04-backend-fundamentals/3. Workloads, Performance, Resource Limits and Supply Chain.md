# Workloads, Performance, Resource Limits and Supply Chain

In the previous note I looked at how requests overlap. Here I follow what happens when more requests arrive than my service can finish, and how I decide what to measure or change. I use Node.js v26 and Express 5 for the server examples.

## 1. CPU-bound and I/O-bound work

I call work CPU-bound when most of its time goes into computation. Image resizing and large calculations are examples. If I run heavy synchronous work in an Express handler, it occupies the main JavaScript thread. Even a quick health check can wait behind it.

I call work I/O-bound when most of its time goes into waiting for a file, database or network response. A handler can be doing both. It might wait for a database response and then spend a lot of CPU time parsing or transforming it.

| What limits my request | How I scale it |
| --- | --- |
| CPU time | I reduce or reuse the computation first. I can move heavy JavaScript into a bounded worker-thread pool or a background job. I add processes or instances when I have more CPU capacity to use. |
| I/O waits | I use asynchronous I/O so waiting requests leave the event loop available. I reduce unnecessary calls, reuse connections and cap concurrent work. I add instances when the app is the bottleneck and the dependency has capacity for more traffic. |

Adding workers cannot give me more CPU cores. Adding app instances can make latency worse if they send more work to a database that is already saturated. I check CPU usage, event-loop delay and downstream timings together before deciding which resource to scale. [Node.js event loop and worker pool](https://nodejs.org/en/learn/asynchronous-work/dont-block-the-event-loop)

## 2. Profiling, latency under load and connection pooling

### I measure latency under load

I start with a representative request mix in a test environment. I warm up the app, increase the request rate in steps and record throughput, errors and latency together. Throughput is how many requests finish per second. I count failures and timeouts separately so fast error responses do not make the run look healthy.

I watch p50, p95 and p99. If p95 is 400 ms, roughly 95 percent of the measured requests finished in 400 ms or less. A steady p50 with a rising p99 tells me to investigate the slow tail. I compare time spent waiting for a pool slot, running the handler and waiting on the downstream service. If throughput flattens while latency rises, I look for a saturated resource or a growing queue.

### I collect CPU and memory profiles

I run these separately against the same Express app and repeat the same workload. I stop Node normally so it can save the profile.

```sh
node --cpu-prof server.mjs
node --heap-prof server.mjs
```

I use the CPU profile to find functions that take a large share of sampled CPU time. I use the heap profile to see where sampled JavaScript allocations come from. If memory keeps growing across repeated runs at the same load, I compare heap snapshots to see which objects and references keep data alive. I check RSS and buffer memory too because the JavaScript heap is only part of the process memory. I compare latency in a separate run because profiling can change the timings. [Node.js CLI profiling options](https://nodejs.org/docs/latest-v26.x/api/cli.html) · [Node.js process memory usage](https://nodejs.org/docs/latest-v26.x/api/process.html#processmemoryusage)

### I reuse database connections

I create one connection pool per app process and reuse it across requests. A request borrows a connection, uses it and returns it. If I borrow one manually for a transaction, I return it in a `finally` block. I give pool acquisition a timeout so a request cannot wait indefinitely for a slot.

If I run four app processes with a pool maximum of ten connections each, they can open up to forty database connections. I count other workers, overlapping deploys and administrative connections when I budget capacity. If the pool is full, I check how long requests wait for a slot and how long queries hold connections before increasing the pool size.

## 3. File descriptors, connection limits and timeouts

An open socket or file uses a file descriptor. I can reach the process limit even when CPU usage is low. On Linux I can run `ulimit -n` to see the current shell's open-file limit. For a deployed process, I check the limit applied by its service manager and compare it with the actual open descriptor count. An `EMFILE` error tells me the process ran out of descriptors. I check for leaked files or sockets and excessive concurrent connections.

One active request can involve a client connection and a separate upstream connection. With keep-alive, a socket can stay open after a request finishes. HTTP/2 can carry multiple requests on one connection, so I track both connections and in-flight requests.

| Layer | What I check |
| --- | --- |
| Client | Connection timeout and total request deadline |
| Load balancer or proxy | Client connection limits, upstream connection timeout, upstream response timeout and idle timeout |
| Node HTTP server | Connection budget, time allowed to receive headers or the full request, and keep-alive idle time |
| Express route | Deadline for handler work, including any downstream calls |
| Database or external API | Pool size, time to acquire a slot, and query or request deadline |

I set inner deadlines so the app has time to handle a failure before the proxy gives up. For example, if a proxy waits 5 seconds and my handler has a 4-second deadline, I could budget 1 second to acquire a database connection and 2 seconds for the query. I keep the remaining time for other handler work and the response. When a deadline expires, I pass cancellation to the operation if its client supports it so abandoned requests do not keep consuming capacity.

In my Express practice server I can set these limits on the Node HTTP server returned by `app.listen()`.

```javascript
const server = app.listen(3000, "127.0.0.1")

server.maxConnections = 200
server.headersTimeout = 5_000
server.requestTimeout = 15_000
server.keepAliveTimeout = 5_000
```

Here I use example values. I choose them based on expected traffic and request sizes. `requestTimeout` limits how long Node waits to receive the request from the client. I still need a deadline for the handler and its dependencies. [Node.js HTTP server options](https://nodejs.org/docs/latest-v26.x/api/http.html) · [Node.js TCP connection limit](https://nodejs.org/docs/latest-v26.x/api/net.html#servermaxconnections)

## 4. Dependency risks and vulnerability scanning

When I add an npm package, I also bring in its transitive dependencies. A package can have a known vulnerability, an abandoned dependency or an install script that runs code on my machine or in CI. Before adding a package, I check that I have the intended package name, look at who maintains it and review the dependencies and install scripts it brings in.

I commit `package-lock.json` with the manifest so the team can review the resolved versions. I run these commands in the project directory that contains both files.

```sh
npm ci
npm audit
```

I read which package is affected, which dependency brought it in, which versions are vulnerable and whether a fixed version is available. I can run `npm explain <package>` to trace the dependency chain after installation. For a direct dependency, I review and update it to a fixed version. For a transitive dependency, I first look for an update to the package that brings it in. I review the lockfile diff, run the app's tests and scan again after the update.

I use the audit report to find known advisories. I still review package provenance and dependency changes because an audit can miss newly published or unreported problems. [npm dependency auditing](https://docs.npmjs.com/auditing-package-dependencies-for-security-vulnerabilities/) · [npm explain](https://docs.npmjs.com/cli/commands/npm-explain/)
