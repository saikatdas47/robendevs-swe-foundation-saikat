# Tenant Isolation, Onboarding and Governance

This note follows the [ShopNest tenant and billing model](1.%20SaaS%20Foundations%2C%20Tenant%20Identity%20and%20Billing.md).

## Tenant isolation across the application

| Layer | Example rule |
| --- | --- |
| Authorisation | Check the user's membership and required action for the active tenant. Fetch an order using both `tenant_id` and `order_id`. A request for another merchant's order should return no data. |
| Database | Include tenant scope in queries and constraints. An order item can reference its parent by `(tenant_id, order_id)` so it cannot point to another tenant's order. PostgreSQL row-level security can add a separate guard. |
| Cache | Use keys like `tenant:42:report:2026-11`. Include the permission scope too if the result differs by role or user. |
| Queues and jobs | Include the tenant ID and job ID in the message. At execution, resolve tenant placement, set tenant context, and scope every read and write. Retry safely with a tenant-scoped idempotency key. |
| Files and search | Scope file paths, signed downloads, search filters, and exports to the tenant. Check access before handing out a download link. |

If PostgreSQL row-level security uses a connection setting for tenant context, set it locally inside a transaction and use the same connection for the queries. A pooled connection must not carry one tenant's context into the next request. Use a runtime role that cannot bypass the policy. Test reads and writes across tenant boundaries, including exports and queued jobs.

### Example failure

Nila Boutique opens a monthly report and sees Dhaka Sneakers' sales. The report used the shared key `report:2026-11`. Both requests received the same cached value even though their database queries were scoped correctly. Disable the affected cache path, clear unsafe entries, and review access logs to see which tenants were affected. Use a tenant-scoped key and test with two merchants requesting the same month.

## Reliable onboarding

| Step | What the platform records or does |
| --- | --- |
| Register | Verify the owner, create a tenant and owner membership, and reserve a unique shop slug. |
| Provision | Pick a deployment location and create default roles, theme, and storage. Create a schema or database if the tenant uses one. |
| Configure | Save the tenant's locale, currency, payment settings, and shop details. Keep payment secrets in a secret store. |
| Activate | Verify the shop is ready, enable its default domain, start the trial when the product policy says it begins, and tell the owner what to do next. |

Persist progress and error details. A retry should resume a failed step using the same tenant and provisioning key. If schema creation succeeds and a later setup step fails, rerunning that workflow should use the existing schema and finish the remaining work.

### Custom domains and TLS

1. Reserve the requested hostname so two tenants cannot claim it at once.
2. Ask the merchant to point DNS at the platform and prove control, for example by adding a verification TXT record.
3. Issue a TLS certificate for the verified name and track renewal. TLS is often called SSL in product settings.
4. Activate the hostname-to-tenant mapping once DNS and the certificate are ready. Validate incoming hostnames against that mapping.
5. When a domain is removed or changes owners, stop serving the old mapping and require new verification before assigning it again.

A domain selects the target shop. Staff requests still need authentication and tenant-specific permission checks.

### Configuration, flags and entitlements

Configuration tells the product how a tenant's shop should run. A **feature flag** controls whether a feature is released to that tenant or cohort. An **entitlement** defines whether the tenant is allowed to use it under the plan, an add-on, or a contract. A Pro shop can have access to abandoned-cart emails under its subscription while a rollout flag keeps the new version off until release. Check both rules on the server, and invalidate cached configuration when either changes.

## Entitlements, quotas and usage metering

| Control | Question it answers | Example |
| --- | --- | --- |
| Entitlement | Can this tenant use the feature? | Only plans with API access can create API credentials. |
| Quota | How much can the tenant have or use? | A shop can create up to 1,000 products on its current plan. |
| Rate limit | How quickly can the tenant perform an action? | Allow up to 100 API requests per minute per shop. |
| Usage meter | How much billable activity happened? | Count SMS sends for the billing period. |

Enforce a hard product quota in the same transaction as the write, for example by updating a tenant counter atomically before adding the product. Two simultaneous requests should not both claim the last slot. Rate limits can use short-lived counters in Redis and return HTTP `429` when the tenant needs to wait. A soft quota can warn the merchant before a hard limit applies.

Store billable usage as durable events with tenant ID, unique event ID, quantity, metric, and event time. Deduplicate retries and record which pricing version and billing period were used. Decide how to handle events arriving after an invoice closes, such as issuing an adjustment. Keep enough detail to explain each invoice line.

## Audit trails, retention and deletion

An audit trail records who performed an action, which tenant and resource it affected, when it happened, and its outcome. Role changes, support access, exports, and deletion requests should leave an audit record. Restrict audit access and avoid logging payment secrets or full customer records.

A retention policy defines how long each data type remains available, including orders, logs, audit entries, files, and backups. Cancellation ends the commercial agreement. Data deletion follows the retention policy, agreed export window, and any legal hold.

Before deleting a tenant, verify the request and block new writes. Run a tracked deletion job that covers the database, object storage, search, cache, and pending jobs. Record completion for each system. Immutable backups can follow a separate expiry schedule. When restoring an older backup, reapply deletion records before returning it to service so deleted tenants do not become active again.
