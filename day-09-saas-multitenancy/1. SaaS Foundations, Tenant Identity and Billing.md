# SaaS Foundations, Tenant Identity and Billing

ShopNest is a fictional service where merchants set up online shops. Rahim's Tea House has a small storefront on a ShopNest subdomain. Dhaka Sneakers has staff accounts and its own domain. Both use the same product.

## SaaS, IaaS and PaaS

| Model | What the provider supplies | What the customer manages | Example |
| --- | --- | --- | --- |
| IaaS | Virtual machines, networking, and storage | OS patches, runtime, app, and data | The ShopNest team runs an app on a virtual machine. |
| PaaS | A managed platform for running application code | App code, settings, data, and access | The team deploys an API to a managed app platform. |
| SaaS | A working application operated by the provider | Account settings, users, and how the app is used | A merchant signs in to ShopNest and creates a storefront. |

The same business can use all three. ShopNest can build on IaaS and PaaS while selling its own product as SaaS.

## Tenants, users and identity

A **tenant** is the customer boundary. For ShopNest it is a merchant account that owns its staff memberships, products, orders, domains, settings, and subscription. A user is a person who can belong to more than one tenant. A membership ties a user to a tenant and gives that user a role there.

| User | Tenant | Role |
| --- | --- | --- |
| Sumi | Dhaka Sneakers | Staff |
| Sumi | Nila Boutique | Owner |

Sumi can change settings for Nila Boutique if the owner role allows it. The Dhaka Sneakers request must be checked against her staff permissions for that shop.

For a staff request to open an order, the server resolves the store from a verified hostname, selected workspace, or validated token claim. It authenticates the user, checks active membership for the resolved tenant, and checks the required permission and resource. Use a stable internal `tenant_id` in the request context and propagate it to downstream work. Route names and domains can change. A supplied tenant ID merely identifies the requested account and still needs permission checks. Public storefront reads follow separate access rules that expose published data only.

## Three tenant data models

| Model | How it works | Cost and operations | Main isolation risk |
| --- | --- | --- | --- |
| Shared schema, or pool | All tenants share tables. Each tenant-owned row has a `tenant_id`. | Low cost per tenant and one set of schema migrations. A per-tenant restore needs a careful export and merge. | A query missing its tenant scope can expose another tenant's rows. Enforce tenant-aware keys and consider row-level security. |
| Schema per tenant, or bridge | One database contains a separate schema for each tenant. | More migrations to coordinate. Exports can target a schema, though tenants still share database resources. | An incorrect schema selection or a connection with broad access can reach the wrong schema. |
| Database per tenant, or silo | Each tenant uses a separate database. Several databases may still share a database server. | More provisioning, connection management, backups, and upgrades. A tenant-level restore is easier to target. | A bad connection mapping, shared service credential, or backup export can still cross a boundary. |

A pooled model can work for many small shops. A dedicated database or deployment can be reserved for tenants with stronger isolation or restore needs. The tenant catalogue records the chosen placement so application routes do not have to guess it.

## Plans, trials and subscriptions

A **plan** groups prices, billing intervals, features, and limits. A **subscription** records which tenant has accepted a plan and for what period. Store the plan version and effective dates so later pricing changes do not rewrite old invoices.

| Example plan | Included features |
| --- | --- |
| Free | ShopNest subdomain and a small product limit |
| Basic | Custom domain and a larger product limit |
| Pro | API access and abandoned-cart emails |

A **trial** grants temporary access. Record when it starts, when it ends, and whether the tenant will convert, drop to Free, or lose trial-only access. When a merchant upgrades halfway through a paid period, proration can charge or credit the price difference for the time left. The billing policy decides when downgrades take effect and what happens to existing data above a lower quota.

### Billing lifecycle

1. Create the trial or paid subscription and record its dates.
2. At renewal, prepare invoice lines for the recurring charge, adjustments, and any billable usage.
3. Attempt payment and reconcile the result against the payment provider's record.
4. If payment fails, mark the account past due and apply the published grace period and retry schedule. A successful retry can return it to active.
5. If retries fail, apply the suspension policy. A cancellation can take effect at the end of the paid period. Data retention and deletion then follow their own schedule.

Payment webhooks can arrive twice or out of order. Verify the signature against the original request body and match the provider subscription to the internal tenant. Store each provider event ID with a uniqueness rule. Update subscription state and record processing in one transaction where possible. For late events, compare the effective period or reconcile with the provider before changing access. This keeps a duplicate payment event from activating the same change twice.
