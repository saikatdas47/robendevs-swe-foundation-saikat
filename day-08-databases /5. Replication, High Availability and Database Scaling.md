# Replication, High Availability and Database Scaling

The examples use the [shop database](1.%20Relational%20Modelling%20and%20SQL.md). PostgreSQL, Amazon RDS, and Redis illustrate different parts of the design. Run the PostgreSQL examples on a practice database.

## Replication

### Write-ahead log and primary/standby

PostgreSQL records changes in a write-ahead log (WAL) before writing the affected data pages to disk. With normal durable commit settings, PostgreSQL flushes the WAL needed for a commit before it reports success. After a crash, it can replay the WAL to recover committed changes whose data pages had not yet been written.

In physical replication, the **primary** accepts writes and sends WAL to a **standby**. The standby receives and replays it to keep a copy of the database. A standby configured to serve queries is called a **hot standby**. A read replica can run catalogue reads or reports while the primary handles checkout writes. [PostgreSQL standby and streaming replication](https://www.postgresql.org/docs/current/warm-standby.html)

### Replication lag and read-after-write consistency

Lag is the gap between the primary's progress and the standby's progress. WAL can be generated faster than the network can deliver it or faster than the standby can replay it. Receiving a change and making that change visible to a query are two different stages.

Suppose checkout commits order 105 on the primary. An immediate request to the order history page goes to a replica that has yet to replay the commit. The new order appears missing even though checkout succeeded.

| Approach | How it handles the example |
| --- | --- |
| Read from the primary after a write | Send the confirmation page and other reads that must see the latest order to the primary. |
| Wait for replica replay | Capture a WAL position at or after the commit on the primary. Read from a replica once its replay position has reached that point. If waiting times out, fall back to the primary or return a retryable result. |
| Use synchronous replication with apply confirmation | In PostgreSQL, `synchronous_commit = remote_apply` waits for configured synchronous standbys to apply the commit. Route the read to a standby that acknowledged it. Waiting adds commit latency. |

**Read-after-write consistency** means a client can read its own successful write. A short period of primary routing can reduce stale reads, but a fixed timer cannot guarantee freshness once it expires.

For PostgreSQL, this sample query runs on the primary and shows WAL that a directly connected standby has yet to replay. Check expected standbys that are missing from the view separately.

```sql
SELECT application_name,
       state,
       pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn) AS pending_replay_bytes
FROM pg_stat_replication;
```

A growing byte gap suggests the standby is falling behind. The byte count measures data, so use a separate freshness or replay-time signal to understand how stale the replica is for readers. [PostgreSQL read-your-writes consistency](https://www.postgresql.org/docs/current/warm-standby.html#SYNCHRONOUS-REPLICATION)

## High availability and recovery

| Mechanism | What it helps with | Shop example |
| --- | --- | --- |
| Multi-AZ and failover | Restore service after a database instance or Availability Zone fails. | A standby takes over after the primary becomes unavailable. |
| Backups | Restore a saved database copy. | Recover the database after storage loss or a destructive mistake. |
| Point-in-time recovery (PITR) | Restore to a chosen time within the available recovery window. | Restore a copy from just before a bulk update changed every order status. |

### Multi-AZ and failover

An Amazon RDS **Multi-AZ DB instance** deployment has a standby in another Availability Zone for failover. That standby does not serve reads. An RDS **Multi-AZ DB cluster** has two standby instances that can also serve reads. Read replicas are a separate way to add read capacity and may lag behind the writer. [Amazon RDS Multi-AZ deployments](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/Concepts.MultiAZ.html) [Amazon RDS read replicas](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_ReadRepl.html)

During failover, the application can lose connections or receive a timeout. Reconnect through the configured endpoint and retry only when the operation is safe to repeat. If checkout loses the response to a commit, the order may already exist. A unique checkout request ID lets the application look up the result before retrying. With asynchronous replication, acknowledged writes that had yet to reach the promoted standby can be lost.

### Backups and point-in-time recovery

A replica also replays unwanted updates and deletes. Backups keep a copy from an earlier point in time. PITR combines a base backup with retained transaction logs to restore to a target time. Amazon RDS restores to a new instance. Check that the data is correct before switching traffic or copying recovered rows back.

**RPO** is how much data loss can be tolerated, measured as time. **RTO** is how long service can be unavailable. A five-minute RPO and a one-hour RTO mean the recovery plan should lose at most five minutes of data and restore service within an hour. A restore drill shows whether the backup, logs, and recovery steps can meet those targets. [Amazon RDS point-in-time recovery](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_PIT.html)

## Scaling writes with partitioning and sharding

### Partitioning within one database

Partitioning divides a large table into smaller physical pieces. In PostgreSQL, an application can still query a single parent table. A query that filters by the partition key can skip irrelevant partitions. This is called **partition pruning**.

For a growing event table, use monthly ranges on the event date. The following PostgreSQL example stores November events in one partition and December events in another. Run it on a fresh practice database.

```sql
CREATE TABLE shop_events (
    event_date date NOT NULL,
    event_id bigint NOT NULL,
    event_type text NOT NULL,
    PRIMARY KEY (event_date, event_id)
) PARTITION BY RANGE (event_date);

CREATE TABLE shop_events_2026_11 PARTITION OF shop_events
FOR VALUES FROM ('2026-11-01') TO ('2026-12-01');

CREATE TABLE shop_events_2026_12 PARTITION OF shop_events
FOR VALUES FROM ('2026-12-01') TO ('2027-01-01');

EXPLAIN
SELECT event_id, event_type
FROM shop_events
WHERE event_date >= DATE '2026-11-01'
  AND event_date < DATE '2026-12-01';
```

The plan should access the November partition only. Range starts are inclusive and ends are exclusive. Create future partitions before inserts need them. This setup makes date-based queries and retention easier, but both partitions still share the same database writer. A busy current month can still limit write throughput. [PostgreSQL table partitioning](https://www.postgresql.org/docs/current/ddl-partitioning.html)

### Sharding across databases

Sharding splits records across separate database servers, each with its own writer. A router sends each request to a shard using a **shard key**. For a shop platform with many merchants, routing by merchant ID can keep a merchant's orders and their items on the same shard.

- Pick a key that spreads writes and matches common requests. A very large merchant can still make one shard hot.
- Keep related writes on one shard when possible. Reports across merchants may need to query several shards or read from a separate reporting store.
- Plan for moving data when shards fill up. Cross-shard joins, transactions, and resharding add work that a single database handles more easily.

A read replica adds capacity for reads. Sharding can add capacity for writes by spreading them across writers. Consider it once measurements show that a single writer is the limit and the workload can be split by a useful key.

## Redis caching with cache-aside

In **cache-aside**, the application checks Redis before reading the database. A cache miss sends the request to the database, and the application puts the result in Redis for later requests. The database remains the source of truth.

1. Read `shop:product:123` from Redis.
2. On a hit, return the cached catalogue data.
3. On a miss, read the product from the database and cache it with a time to live (TTL).
4. On a product edit, commit the database change, then delete the cache key. The next cache miss loads the new value.

```text
GET shop:product:123
SET shop:product:123 '{"id":123,"name":"Notebook","price_cents":500}' EX 60
DEL shop:product:123
```

A TTL sets how long an entry may stay in the cache before it expires. Use shorter TTLs for rapidly changing values. Longer TTLs can cut database reads when values stay stable. Add a small random offset to TTLs when many keys might otherwise expire together. If many requests can refill the same popular key, allow one request to refill it while the others wait or use an acceptable stale value.

Invalidating after commit avoids clearing the key before a failed update, but stale data can still come back. A reader may fetch the old row before the write commits and cache it after the delete. Use bounded TTLs and consider version checks if that race matters. For checkout, read and validate the current price and stock against the database even if the catalogue page uses Redis. [Redis cache-aside guide](https://redis.io/docs/latest/develop/use-cases/cache-aside/)

## PostgreSQL internals

### Vacuum and bloat

PostgreSQL uses MVCC to let transactions see the row versions that belong to their snapshots. Updates create new versions. Deletes mark rows as removed for newer snapshots. Old versions remain available while an active snapshot could still need them.

**VACUUM** cleans up versions that are safe to remove and makes their space available for future writes. It also maintains visibility information and helps prevent transaction ID wraparound. **Autovacuum** runs maintenance automatically. Long-running transactions can prevent cleanup, so a growing table may need investigation even if autovacuum is running.

**Bloat** is extra space in a table or index compared with the space needed for its current data. An orders table that changes status often can build up dead rows and unused space. Plain vacuum usually makes space reusable inside the relation. `VACUUM FULL` rewrites the table to reclaim more disk space and holds an exclusive table lock. Schedule a rewrite only after checking the cause and the impact. [PostgreSQL routine vacuuming](https://www.postgresql.org/docs/current/routine-vacuuming.html)

### Optimiser statistics

**ANALYZE** samples table data and stores statistics such as common values, approximate distinct counts, and value distributions. The optimiser uses them to estimate how many rows will match a filter and to choose scans and joins.

If almost all orders are paid, a query for paid orders may use a table scan because it expects to read most rows. A query for the few pending orders may benefit from an index. After a bulk import or a big change in the status distribution, refresh statistics and compare the plan's estimates with actual rows. If columns are strongly related, PostgreSQL can collect extended statistics so the planner can estimate some combined filters more accurately. [PostgreSQL planner statistics](https://www.postgresql.org/docs/current/planner-stats.html)

```sql
SELECT relname, n_live_tup, n_dead_tup, last_autovacuum, last_autoanalyze
FROM pg_stat_user_tables
WHERE relname = 'orders';

VACUUM (ANALYZE) orders;

EXPLAIN (ANALYZE, BUFFERS)
SELECT order_id FROM orders WHERE status = 'pending';
```

Run `VACUUM` outside a transaction block. The row counts in `pg_stat_user_tables` are estimates. Compare the plan on data large enough to represent the workload before drawing conclusions about index use or performance.
