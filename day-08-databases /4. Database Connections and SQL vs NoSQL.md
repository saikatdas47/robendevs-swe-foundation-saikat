# Database Connections and SQL vs NoSQL

The examples build on the [shop database](1.%20Relational%20Modelling%20and%20SQL.md). The shop has orders and payments, a product catalogue, shopping carts, and an event feed. Each feature uses data in a different way.

## Connection pooling

A database connection is an open session between the application and the database. Opening a new one can involve a network handshake, TLS, and authentication. The database also spends resources keeping connections open, even when some are idle.

A connection pool keeps a limited set of connections ready to reuse. A request borrows a connection, runs its SQL, and returns the connection. If every connection is busy, requests wait up to an acquisition timeout. A long wait can point to slow queries, long transactions, or more traffic than the current database can handle.

### How an application uses a pool

1. Create one reusable pool per application process. Avoid creating a new pool on each request.
2. Let the driver borrow and return a connection for a single independent query when its pool API supports that.
3. For a transaction, borrow one connection and use it for every statement from begin to commit or rollback.
4. Return the connection even if a statement fails. If the connection is broken or rollback fails, discard it through the pool instead of returning it as healthy.

For example, saving an order and its items uses one borrowed connection until the transaction ends. A payment gateway call can take much longer than the SQL, so the application should avoid holding the connection open while waiting for it.

### Size the pool across the whole application

A pool limit usually applies to one process. Five processes with a limit of 12 can open up to 60 database connections. During a rolling deployment, ten processes could briefly open up to 120. Include background workers and leave room for migrations, monitoring, and admin access.

Track active connections, how long callers wait to borrow one, and acquisition timeouts. Raising the pool limit can shift the queue into the database and slow down more requests if the database is already busy. A pool acquisition timeout limits time spent waiting for a connection. A statement timeout limits time spent running an individual query.

## Amazon RDS Proxy

RDS Proxy is a managed connection pool that sits between the application and a supported RDS or Aurora database. The application connects to the **proxy endpoint**. The proxy opens and reuses backend database connections. When it is safe to share a backend connection, the proxy can lend it to another client after a transaction ends. This is called **multiplexing**. [Amazon RDS Proxy documentation](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/rds-proxy.html)

```text
Application processes or Lambda functions
                  |
           RDS Proxy endpoint
                  |
         Pooled DB connections
                  |
           RDS or Aurora DB
```

- **When it helps** — A Lambda function or a service that scales out quickly can open many client connections in a short time. A proxy can absorb some of that churn by reusing database connections.
- **When a local pool may be enough** — A few long-running app processes with stable traffic and low connection wait times may already manage database connections well.
- **When the proxy is busy** — Callers can wait for a backend connection or hit the proxy's borrow timeout. The underlying database still has a finite amount of CPU, memory, and throughput.
- **During failover** — The proxy can reconnect to the new database target and preserve client connections where possible. An in-flight transaction can still fail. Handle errors and only retry work that is safe to repeat.

### Session pinning

If later statements depend on state that belongs to one database session, the proxy may keep that client tied to one backend connection. This is called **pinning**. A temporary table or a session setting can cause it, depending on the database engine. A pinned connection stays reserved for that client until the session ends, so frequent pinning reduces the benefit of the pool. [AWS guide to RDS Proxy pinning](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/rds-proxy-pinning.html)

When evaluating the proxy, compare the number of client and database connections, watch how long clients wait to borrow a connection, and check how many sessions are pinned. Keep any application-side pool bounded as well.

## SQL vs NoSQL

A relational database stores related facts in tables and uses keys, constraints, joins, and transactions to work with them. NoSQL covers several data models. Choose based on the reads and writes the application needs, which rules must hold during an update, and how the data will grow. Transaction, indexing, and consistency guarantees vary by product.

| Model | How data is read | Good fit | Trade-off to check |
| --- | --- | --- | --- |
| Relational, such as PostgreSQL | Filter rows, join tables, or group results. | Orders, payments, inventory, and reporting. | Large joins and hot rows still need careful queries, indexes, and transaction design. |
| Document, such as MongoDB | Read a document by ID or filter by fields inside it. | Product catalogues with different attributes and records often read as a whole. | Embedded data can grow or be copied into several documents. |
| Key-value, such as Redis | Look up a value by a key the application already knows. | Caches, short-lived carts, session state, and counters. | Plan expiry, persistence, and any searches that need more than a key. |
| Wide-column, such as Cassandra | Read rows in a partition, often in clustering-key order. | High-volume event history with known lookup patterns. | Partition design matters. A new lookup pattern may need another table. |

### Relational database — orders and payments

Use related tables when the application needs database rules across records or needs to ask many different questions about the same data. In the shop, an order item must refer to a valid product, a checkout must save the order and its items together, and a report may group paid sales by customer or month. A relational model supports those patterns through foreign keys, transactions, and SQL queries.

### Document store — product catalogue

A document groups fields and nested objects into one record. A shirt may have size and fabric fields, while a laptop has memory and storage. Both can live in one catalogue and share fields such as name and category.

```json
{
  "_id": "shirt-123",
  "name": "Linen shirt",
  "category": "clothing",
  "attributes": {
    "fabric": "linen",
    "sizes": ["S", "M", "L"]
  }
}
```

Embed small details that usually load with the product. Store large or growing collections such as reviews separately when they are read and updated on their own. Add validation for fields the app relies on and index the fields used in common queries. [MongoDB data modelling](https://www.mongodb.com/docs/manual/data-modeling/)

### Key-value store — temporary cart

The application knows the session ID and can build a key such as `cart:guest-42`. Redis can store a small JSON string at that key and expire it after an hour.

```text
SET cart:guest-42 '{"productId":1,"quantity":2}' EX 3600
GET cart:guest-42
```

This fits a short-lived cart lookup. A question such as “which carts contain product 1?” needs a separate lookup structure or a store that can query by product. Keep placed orders in durable storage and decide how a guest cart should behave after expiry. [Redis SET documentation](https://redis.io/docs/latest/commands/set/)

### Wide-column store — device events by day

A shop may collect a large stream of device events. If the main query is “show the latest events for this device on this day,” a Cassandra table can use `(device_id, event_day)` as a composite partition key and `event_id` as a clustering key. A time-based `event_id` orders events within each partition and distinguishes events recorded close together.

The date groups events into smaller partitions instead of putting all history for a device in one place. Choose the time bucket based on how many events arrive and how the app reads them. If a busy device still makes one day's partition too large, a shorter bucket may help. A separate query such as “show events by site” can need a table built around the site lookup. The application then has to keep both views of the data up to date. [Apache Cassandra data modelling](https://cassandra.apache.org/doc/latest/cassandra/developing/data-modeling/intro.html)

### Choosing for the shop

Start with the reads, writes, and rules that are already known. A relational database can handle the main shop workload. A document store can help when catalogue items have different shapes and are usually read as whole records. A key-value store fits short-lived lookups by exact key. A wide-column store fits a large event workload where queries follow known partition keys. Add another store when its access pattern or scale justifies the extra work of running it and keeping data consistent.
