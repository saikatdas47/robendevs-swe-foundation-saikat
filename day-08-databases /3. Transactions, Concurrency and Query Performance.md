# Transactions, Concurrency and Query Performance

The examples use the [shop schema and sample data](1.%20Relational%20Modelling%20and%20SQL.md). The transaction and query examples run in SQLite unless marked PostgreSQL. For a two-session example, open two separate connections to the same practice database.

## Transactions and ACID

A transaction groups SQL statements into one unit of work. An order and its items should be saved together. If saving an item fails, the application should roll back the transaction so that an incomplete order is not saved.

| Property | Meaning | Shop example |
| --- | --- | --- |
| Atomicity | The changes commit together or are rolled back together. | An order and its items are saved as one unit. |
| Consistency | A committed transaction preserves the rules enforced by the database and the application. | A foreign key prevents an order item from referring to a missing product. The application must still check business rules such as whether the order has any items. |
| Isolation | The isolation level controls what concurrent transactions can see and how they can affect each other. | A report should only count an order once its transaction has committed. |
| Durability | Once a commit succeeds, its changes survive a crash under the database's durability settings. | A committed order is still present after the database restarts. |

```sql
BEGIN;

INSERT INTO orders (order_id, customer_id, order_date)
VALUES (105, 3, '2026-11-09');

INSERT INTO order_items (order_id, product_id, quantity, unit_price_cents)
VALUES (105, 1, 2, 500);

COMMIT;
```

Use the same connection for all statements in the transaction. If any statement fails, issue `ROLLBACK` and report the error. In SQLite, a constraint violation can fail just the current statement and leave the transaction open. To try it on a fresh copy, change the quantity to zero, stop when the insert fails, roll back, and check that order 105 is absent.

### Isolation levels

| Level | What the SQL standard permits | PostgreSQL behaviour |
| --- | --- | --- |
| Read Uncommitted | Dirty reads, non-repeatable reads, phantoms, and serialisation anomalies. | Behaves like Read Committed. |
| Read Committed | Non-repeatable reads, phantoms, and serialisation anomalies. | The default. Each ordinary SELECT sees a snapshot taken at the start of that statement. |
| Repeatable Read | Phantoms and serialisation anomalies. | Ordinary reads share a snapshot taken at the first statement that needs one. Phantoms are prevented, but write skew is still possible. |
| Serializable | Successful transactions have the same effect as some one-at-a-time order. | PostgreSQL can abort a transaction with SQLSTATE `40001` when it cannot guarantee that result. Retry the whole transaction. |

- **Dirty read** — A checkout reads a product price that another transaction has changed but might still roll back.
- **Non-repeatable read** — A report reads the same order twice and sees its status change from pending to paid after another transaction commits.
- **Phantom read** — A report repeats a query for paid orders and finds an additional matching row after another transaction commits.
- **Write skew** — Two staff members each see that the other is on shift, so both remove themselves by updating different rows. Each update alone looks valid. Together they leave nobody on shift.

### See a snapshot in two PostgreSQL sessions

Start with order 103 in its original `pending` state. Run these statements in the order shown by the comments.

```sql
-- Session A
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT status FROM orders WHERE order_id = 103;

-- Session B
BEGIN;
UPDATE orders SET status = 'paid' WHERE order_id = 103;
COMMIT;

-- Session A
SELECT status FROM orders WHERE order_id = 103;
COMMIT;
SELECT status FROM orders WHERE order_id = 103;
```

Session A sees `pending` inside the transaction and `paid` after committing. With `READ COMMITTED`, its second read would see `paid` as well. Reset order 103 to `pending` before repeating the exercise. [PostgreSQL transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html)

## Concurrency

### Locks

A lock makes conflicting work wait. PostgreSQL automatically locks rows changed by an `UPDATE` or `DELETE`. Use `SELECT ... FOR UPDATE` when a decision depends on the current row and another transaction must not change that row before the decision is saved.

```sql
-- PostgreSQL
BEGIN;
SELECT status FROM orders WHERE order_id = 103 FOR UPDATE;
UPDATE orders SET status = 'paid'
WHERE order_id = 103 AND status = 'pending';
COMMIT;
```

Another transaction trying to update that same row can wait until the first finishes. A plain SELECT can still read a visible version. When the only rule is “change pending to paid,” the conditional UPDATE alone is enough. Check the affected row count to tell whether the transition happened.

### MVCC

Multi-version concurrency control (MVCC) lets PostgreSQL keep multiple versions of a row. A reader uses the version visible to its snapshot. A writer can produce a new version while a reader still sees the old one. Writers changing the same row can still block each other. Long transactions can keep old versions around and delay cleanup.

SQLite allows one writer at a time. In write-ahead log (WAL) mode, a reader can keep reading its snapshot while a writer commits changes. SQLite uses its own concurrency rules and does not support PostgreSQL's `SELECT ... FOR UPDATE`. [SQLite isolation](https://sqlite.org/isolation.html)

### Deadlocks

A deadlock is a cycle of waits. A long wait by itself is ordinary lock contention.

| Step | Session A | Session B |
| --- | --- | --- |
| 1 | Begins and locks order 101 with `SELECT ... FOR UPDATE`. | Begins and locks order 102 with `SELECT ... FOR UPDATE`. |
| 2 | Tries to lock order 102 and waits. | Tries to lock order 101 and waits. |
| 3 | PostgreSQL aborts one transaction to break the cycle. | The other can continue once the conflicting lock is released. |

When several rows need locking, take them in the same order across code paths, such as lowest order ID first. Keep the transaction short and finish it before calling an external service. On a PostgreSQL deadlock (`40P01`), roll back the failed transaction and retry the whole unit of work if it can be repeated safely. Use a bounded retry count with a short delay. [PostgreSQL locking and deadlocks](https://www.postgresql.org/docs/current/explicit-locking.html)

## Query performance

### Read the plan with EXPLAIN

A query plan shows the steps the engine chooses to find, join, group, or sort rows. Start with the scans at the bottom of the plan and follow where their rows go. A table scan reads through a table and can be the right choice for a small table or a query that needs most rows. An index search can visit a smaller range of keys. A sort or temporary structure may add work before results are returned.

In SQLite, run this query plan on a fresh copy of the sample database, then create the index and run the same plan again.

```sql
EXPLAIN QUERY PLAN
SELECT order_id, order_date
FROM orders
WHERE customer_id = 1
ORDER BY order_date DESC, order_id DESC
LIMIT 5;

CREATE INDEX IF NOT EXISTS idx_orders_customer_date
ON orders (customer_id, order_date DESC, order_id DESC);

EXPLAIN QUERY PLAN
SELECT order_id, order_date
FROM orders
WHERE customer_id = 1
ORDER BY order_date DESC, order_id DESC
LIMIT 5;
```

The sample plan changes from `SCAN orders` with a temporary sort to `SEARCH orders` using the covering index. A covering index contains all the columns the query needs. The result stays the same. Order 102 comes before 101. Plain `EXPLAIN` in SQLite shows the lower-level instructions of its virtual machine. [SQLite query plan guide](https://sqlite.org/eqp.html)

In PostgreSQL, `EXPLAIN` shows the estimated plan without running the statement. `EXPLAIN (ANALYZE, BUFFERS)` runs it and shows actual time, row counts, loops, and buffer activity. Compare estimated rows with actual rows and pay attention to nodes that run many times. PostgreSQL costs are planner units rather than milliseconds, and actual row counts shown for a node are per-loop averages when it runs more than once. Use a SELECT for practice since adding `ANALYZE` to a write executes the write. [PostgreSQL EXPLAIN guide](https://www.postgresql.org/docs/current/using-explain.html)

### B-tree and composite indexes

A B-tree keeps keys in sorted order in a balanced tree. The engine follows branches to find a key, then reads nearby entries for a range. This makes B-tree indexes useful for equality filters, ranges, and some sorts. Indexes also need disk space and must be updated when indexed data changes.

A composite index has more than one key column. The shop index groups entries by `customer_id`, sorts each customer's entries by descending date, and uses descending order ID to break ties.

| Query pattern | How the index helps |
| --- | --- |
| `WHERE customer_id = 1` | Finds the range for one customer. |
| `WHERE customer_id = 1 AND order_date >= '2026-11-01'` | Narrows the range further using the date. |
| One customer plus `ORDER BY order_date DESC, order_id DESC` | Can return rows in the requested order and stop early for a small LIMIT. |
| `WHERE order_date >= '2026-11-01'` across all customers | Date is not the leading key. The planner may prefer another index or a scan. Check the plan before adding an index. |

Choose index columns based on the filters and sort order of real queries. Once a range filter is used on a key, later keys usually do less to narrow the scan. Test with realistic data because the planner may choose differently on four rows and four million rows. [PostgreSQL multicolumn indexes](https://www.postgresql.org/docs/current/indexes-multicolumn.html)

### The N+1 problem

Suppose a page loads the latest 20 orders, then asks the database for each order's items in a loop. That is one query for the page and up to 20 more for its items. Even if each lookup is indexed, repeated calls still cost time. This often happens when an ORM loads a relationship only when code first accesses it.

**Option 1 — Load items in one batch.** Run the order query, collect the returned IDs, then run one item query with a bound parameter for each ID. Group the rows by order ID in the application. Skip the item query when the page is empty. In the example below, the parameters are 104, 103, and 102 on the original dataset.

```sql
SELECT order_id, order_date
FROM orders
ORDER BY order_date DESC, order_id DESC
LIMIT 3;

SELECT order_id, product_id, quantity
FROM order_items
WHERE order_id IN (?, ?, ?)
ORDER BY order_id, product_id;
```

**Option 2 — Join the page and its items.** Apply the limit to orders first. Limiting after the join can cut off items or return fewer orders than requested. The left join keeps an order even if it has no items.

```sql
WITH order_page AS (
    SELECT order_id, order_date
    FROM orders
    ORDER BY order_date DESC, order_id DESC
    LIMIT 3
)
SELECT o.order_id, o.order_date, i.product_id, i.quantity
FROM order_page AS o
LEFT JOIN order_items AS i ON i.order_id = o.order_id
ORDER BY o.order_date DESC, o.order_id DESC, i.product_id;
```

A join returns one row per item and repeats the order columns. Batching can avoid that repetition. Check the SQL log or query count for one page request to verify that the number of queries no longer grows with the number of orders.
