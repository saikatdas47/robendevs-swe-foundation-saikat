# Normalisation, Indexes and Migrations

The examples build on the [shop database](1.%20Relational%20Modelling%20and%20SQL.md).

## Normalisation

Normalisation puts facts in the tables where they belong. It reduces repeated data and prevents copies of the same fact from getting out of sync. A functional dependency means one value or set of values determines another. For example, a customer ID determines the customer's current name.

Start with a shop record that stores each order, the customer's name, and a list of products in one row.

### First normal form (1NF)

Keep one value in each field. Replace a list such as `Notebook x2, Pen x3` with one row per order and product. The key for the example below is `(order_id, product_id)`.

| order_id | product_id | order_date | customer_id | customer_name | product_name | quantity |
| --- | --- | --- | --- | --- | --- | --- |
| 101 | 1 | 2026-11-01 | 1 | Asha | Notebook | 2 |
| 101 | 2 | 2026-11-01 | 1 | Asha | Pen | 3 |

The rows are now in 1NF. The date and customer details still repeat across items on the same order.

### Second normal form (2NF)

Start with 1NF and make sure each non-key column depends on the whole key. In the table above, `order_date` depends only on `order_id`, while `product_name` depends only on `product_id`. Move those facts into separate tables.

| Table | Columns |
| --- | --- |
| `orders` | `order_id` (key), `order_date`, `customer_id`, `customer_name` |
| `products` | `product_id` (key), `product_name` |
| `order_items` | `order_id` and `product_id` (combined key), `quantity` |

Quantity depends on both IDs. It describes how many units of a specific product were bought on a specific order.

### Third normal form (3NF)

Start with 2NF and remove indirect dependencies between non-key columns. In `orders`, `order_id` determines `customer_id`, which in turn determines the current `customer_name`. Move the name to `customers(customer_id, name)` and keep `customer_id` as a foreign key in `orders`. A name change now needs one update.

The shop schema also keeps `unit_price_cents` in `order_items`. This is the price charged for that item on that order. The product table holds the current price, which can change later.

### When to denormalise

Denormalisation stores a copy or a calculated value to make specific reads cheaper. For example, a dashboard that repeatedly sums millions of order items could read from a daily sales summary table. Use this when a measured query is still too slow after checking the query and its indexes.

Keep order items as the source of truth. Decide how the summary is refreshed, how much delay is acceptable, and how to rebuild it if a refresh fails.

## Indexes

An index is a data structure that helps the database find rows without reading the whole table. It takes storage and adds work to inserts, updates, and deletes because the database must keep it up to date.

Add an index for a frequent query that filters, joins, or sorts by the same columns, especially once the table grows. Primary keys and unique constraints already provide indexed lookups in SQLite. A foreign key on the child table does not automatically get an index.

This example looks up one customer's latest orders. A composite index starts with `customer_id` for the equality filter, then follows the sort order. The order ID breaks ties when two orders have the same date.

```sql
CREATE INDEX idx_orders_customer_date
ON orders (customer_id, order_date DESC, order_id DESC);

EXPLAIN QUERY PLAN
SELECT order_id, order_date
FROM orders
WHERE customer_id = 1
ORDER BY order_date DESC, order_id DESC
LIMIT 5;
```

Run the query plan before and after adding the index. Look for a search using `idx_orders_customer_date` and check whether a separate sort is still needed. The index can also help a lookup by `customer_id` alone. An order-date filter across all customers may need a different index because `order_date` is not the leading column.

Skip an index that duplicates an existing one or brings little benefit. Measure on data close to the size and shape of the real workload.

## Schema changes and migrations

A migration is a versioned change to the database. Store migrations with the application code and run them in order. A migration tool records which versions succeeded so the same change is applied once per database.

### Write and run an additive migration

Suppose the shop needs a tracking number for orders that have shipped. Add a nullable column because existing orders may have no tracking number. For an SQLite practice database, the following is the content of a migration such as `001_add_tracking_number.sql`.

```sql
BEGIN;

ALTER TABLE orders ADD COLUMN tracking_number TEXT;

COMMIT;
```

With the shop schema already loaded into `shop.db`, the SQLite CLI can run the saved SQL with `sqlite3 -bail shop.db < 001_add_tracking_number.sql`. The plain CLI does not record migration versions, so use this command once for the exercise. When using a migration tool that already wraps changes in a transaction, leave transaction control to that tool.

Verify that existing orders are intact and that the new column starts empty.

```sql
SELECT order_id, tracking_number
FROM orders
ORDER BY order_id;
```

Expected rows are order IDs 101 through 104 with `NULL` in the new column.

### Roll out changes safely

1. Test the migration on a copy with existing data. Check the result and note how long the change takes.
2. Apply additive changes before deploying code that needs them. For a new required field, add it as nullable first, deploy code that fills it, and backfill old rows before enforcing the constraint.
3. Verify the schema and row counts after running the migration. Check that existing reads and writes still work.
4. For destructive changes, test the recovery plan. Dropping a column can discard data, so reversing the schema alone may not restore it.
