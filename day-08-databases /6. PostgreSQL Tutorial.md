# PostgreSQL Tutorial

Build a small shop database in PostgreSQL. The exercises cover connecting with `psql`, creating a schema, working with rows, reading a query plan, and restoring a backup. Run the sections in order on a fresh practice database.

## 1. Connect with psql

PostgreSQL is the database server. `psql` is a terminal client that sends SQL to the server. Start a local PostgreSQL server and make sure the command-line tools are available. Use the database role and connection settings from the local installation. The commands below assume those defaults already work and the role can create databases. [PostgreSQL tutorial](https://www.postgresql.org/docs/current/tutorial.html)

Run these in the terminal.

```bash
psql --version
createdb shop_pg_lab
psql -v ON_ERROR_STOP=1 -d shop_pg_lab
```

If the server requires an explicit host or role, pass `-h localhost -U your_role` to the database tools. Add `-p` with the port if it differs from the local default. `psql --version` checks the client installation. Once connected, `SELECT version();` shows the server version.

These commands run inside `psql`.

| Command | What it does |
| --- | --- |
| `\conninfo` | Shows the current database connection. |
| `\l` | Lists databases. |
| `\dt` | Lists visible tables. |
| `\d orders` | Shows the columns, indexes, and constraints for the orders table. |
| `\q` | Exits to the terminal. |

Backslash commands run directly in `psql). End SQL statements with a semicolon. [psql reference](https://www.postgresql.org/docs/current/app-psql.html)

## 2. Create the tables and add sample data

A database can contain several schemas. A schema groups named objects such as tables. This tutorial uses the default search path in a fresh database. Use identity columns for generated IDs, `date` for order dates, and integer cents for prices.

```sql
CREATE TABLE customers (
    customer_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name text NOT NULL,
    email text NOT NULL UNIQUE
);

CREATE TABLE products (
    product_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    sku text NOT NULL UNIQUE,
    name text NOT NULL,
    price_cents integer NOT NULL CHECK (price_cents >= 0)
);

CREATE TABLE orders (
    order_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id bigint NOT NULL REFERENCES customers (customer_id),
    order_date date NOT NULL DEFAULT CURRENT_DATE,
    status text NOT NULL DEFAULT 'pending'
        CHECK (status IN ('pending', 'paid', 'cancelled'))
);

CREATE TABLE order_items (
    order_id bigint NOT NULL REFERENCES orders (order_id),
    product_id bigint NOT NULL REFERENCES products (product_id),
    quantity integer NOT NULL CHECK (quantity > 0),
    unit_price_cents integer NOT NULL CHECK (unit_price_cents >= 0),
    PRIMARY KEY (order_id, product_id)
);

INSERT INTO customers (name, email) VALUES
    ('Asha', 'asha@example.com'),
    ('Rafi', 'rafi@example.com'),
    ('Mina', 'mina@example.com');

INSERT INTO products (sku, name, price_cents) VALUES
    ('NOTE-01', 'Notebook', 500),
    ('PEN-01', 'Pen', 200);

INSERT INTO orders (customer_id, order_date, status) VALUES
    (1, DATE '2026-11-01', 'paid'),
    (1, DATE '2026-11-03', 'paid'),
    (2, DATE '2026-11-04', 'pending');

INSERT INTO order_items VALUES
    (1, 1, 2, 500),
    (1, 2, 3, 200),
    (2, 1, 1, 500),
    (3, 2, 2, 200);
```

The sample IDs are predictable on this fresh database. Application code should read generated IDs with `RETURNING` or look up rows using a stable key. Identity values can have gaps. They are identifiers, so avoid using them to count records.

## 3. Read and group rows

Join the order and item tables, then total each paid order. Cast the unit price to `bigint` before multiplying to give the calculation room for larger values.

```sql
SELECT o.order_id, c.name,
       SUM(i.quantity * i.unit_price_cents::bigint) AS total_cents
FROM orders AS o
JOIN customers AS c ON c.customer_id = o.customer_id
JOIN order_items AS i ON i.order_id = o.order_id
WHERE o.status = 'paid'
GROUP BY o.order_id, c.name
ORDER BY o.order_id;
```

Expected rows are `(1, Asha, 1600)` and `(2, Asha, 500)`. To find customers who have never ordered, use `NOT EXISTS`.

```sql
SELECT c.name
FROM customers AS c
WHERE NOT EXISTS (
    SELECT 1
    FROM orders AS o
    WHERE o.customer_id = c.customer_id
)
ORDER BY c.name;
```

Expected result is `Mina`.

## 4. Insert, update, and delete safely

This insert uses PostgreSQL's `ON CONFLICT` clause. If the SKU is already present, the statement updates the existing row. `EXCLUDED` refers to the row proposed by the insert. `RETURNING` shows the row that was written. Past order totals still use the prices saved in `order_items`.

```sql
INSERT INTO products (sku, name, price_cents)
VALUES ('NOTE-01', 'Notebook', 550)
ON CONFLICT (sku) DO UPDATE
SET price_cents = EXCLUDED.price_cents
RETURNING product_id, sku, price_cents;
```

Expected row is `(1, NOTE-01, 550)`. Use a transaction to preview other changes and undo them during practice.

```sql
BEGIN;

UPDATE orders
SET status = 'paid'
WHERE order_id = 3 AND status = 'pending'
RETURNING order_id, status;

DELETE FROM customers
WHERE email = 'mina@example.com'
RETURNING name;

ROLLBACK;

SELECT status FROM orders WHERE order_id = 3;
SELECT name FROM customers WHERE email = 'mina@example.com';
```

Inside the transaction, the statements return order 3 as `paid` and show `Mina` as deleted. After rollback, order 3 is `pending` and Mina still exists. Use `COMMIT` when the changes should become permanent.

## 5. Try a view and a window function

A view saves a query under a name. PostgreSQL runs the underlying query when it reads a regular view. A window function calculates across related rows while keeping one output row per order.

```sql
CREATE VIEW customer_order_history AS
SELECT order_id, customer_id, order_date, status,
       ROW_NUMBER() OVER (
           PARTITION BY customer_id
           ORDER BY order_date DESC, order_id DESC
       ) AS order_rank
FROM orders;

SELECT customer_id, order_id, status
FROM customer_order_history
WHERE order_rank = 1
ORDER BY customer_id;
```

Expected rows are `(1, 2, paid)` and `(2, 3, pending)`. Mina has no order rows, so this view has no row to rank for her.

## 6. Add an index and inspect the plan

This query asks for the latest orders from one customer. The index starts with the customer ID used in the filter. Date and order ID follow in the order used for sorting. The order ID breaks ties when two orders share a date.

```sql
CREATE INDEX idx_orders_customer_date
ON orders (customer_id, order_date DESC, order_id DESC);

ANALYZE orders;

EXPLAIN (ANALYZE, BUFFERS)
SELECT order_id, order_date
FROM orders
WHERE customer_id = 1
ORDER BY order_date DESC, order_id DESC
LIMIT 5;
```

Run the SELECT without `EXPLAIN` to see orders 2 and 1 in that order. The practice table has only three rows, so an ordinary table scan and a sort may cost less than using the index. Look at estimated rows, actual rows, and the scan and sort nodes. The `ANALYZE` option executes the statement, so use a SELECT for this exercise. [PostgreSQL query plans](https://www.postgresql.org/docs/current/using-explain.html)

## 7. Back up and restore the practice database

Exit `psql` with `\q`. Run these commands in the terminal. The custom-format backup can be read by `pg_restore`. The restore uses a separate, empty database.

```bash
pg_dump --format=custom --file=shop_pg_lab.dump shop_pg_lab
createdb shop_pg_restore
pg_restore --exit-on-error --dbname=shop_pg_restore shop_pg_lab.dump
psql -d shop_pg_restore -c "SELECT COUNT(*) FROM orders"
```

The restored order count should be 3 after the rollback exercise. Also check that the notebook price is 550 cents. A backup is useful once its contents can be restored and checked. [pg_dump](https://www.postgresql.org/docs/current/app-pgdump.html) [pg_restore](https://www.postgresql.org/docs/current/app-pgrestore.html)
